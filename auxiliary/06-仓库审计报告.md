## 1 · 🔴 硬错误（说法与实测相反）

### 1.1 `const/README.md` —— const vs `#define`，两条都错反了

**原文**：

> - 「const 定义常量从汇编的角度来看，只是给出了对应的内存地址，而不是像 `#define` 一样给出的是立即数。」
> - 「const 定义的常量在程序运行过程中只有一份拷贝，而 `#define` 定义的常量在内存中有若干个拷贝。」

**实测 ①：`-O2` 下 const 和宏编译成完全一样的代码**

```bash
cat > cst.cpp <<'EOF'
const int c = 42;
#define M 42
int f(){ return c; }
int g(){ return M; }
EOF
g++ -std=c++17 -O2 -S cst.cpp -o - | grep -A 3 -E '^_Z1fv:|^_Z1gv:'
```

```text
_Z1fv:              _Z1gv:
    movl $42, %eax      movl $42, %eax
    ret                 ret
```

**两者都是立即数。** const 照样被常量折叠。

**实测 ②：「只有一份拷贝」正好反了**：

```bash
# 两个 TU 各自定义 const int c，值不同
cat > p1.cpp <<'EOF'
const int c = 1;
extern "C" int a(){ return c; }
EOF
cat > p2.cpp <<'EOF'
const int c = 2;
extern "C" int b(){ return c; }
EOF
cat > p4.cpp <<'EOF'
#include <cstdio>
extern "C" { int a(); int b(); }
int main(){ int x=a(), y=b(); std::printf("a()=%d  b()=%d\n", x, y); }
EOF
g++ -std=c++17 p1.cpp p2.cpp p4.cpp -o p4 && ./p4
nm -C p1.o p2.o | grep -v '^$'
```

```text
a()=1  b()=2            ← 两份不同的值，链接通过 = 各有一份

p1.o:  T a     p2.o:  T b
       r c            r c      ← 小写 r = 局部符号 = 内部链接
```

**`#define` 反而根本不产生符号**（`nm` 里找不到），谈不上「若干份拷贝」。

**根因：这是把 C 的知识搬到 C++ 了**（本报告最有价值的发现之一）

```bash
echo 'const int c = 42;' > x.c
gcc -c x.c -o x_c.o              && echo "C  : $(nm x_c.o | grep ' c$')"
g++ -c x.c -o x_pp.o -x c++      && echo "C++: $(nm x_pp.o | grep ' c$')"
```

```text
C  : R c      ← 大写 = 外部链接（两个 TU 都写会 multiple definition）
C++: r c      ← 小写 = 内部链接（每个 TU 各一份，互不冲突）
```

**✅ 正确说法**：

| | `#define M 42` | `const int c = 42;` |
| --- | --- | --- |
| 是什么 | **预处理期的文本替换** | **一个真正的变量** |
| 有名字吗 | ❌（预处理后消失） | ✅ |
| 有类型吗 | ❌ | ✅ |
| 有作用域吗 | ❌（从定义点到文件尾） | ✅ |
| 有链接性吗 | ❌ | ✅（C++ 命名空间作用域 `const` = **内部链接**） |
| 编译成什么 | 由使用处决定 | 由优化器决定（`-O2` 下就是立即数） |

**一句话**：它们的区别是「**是不是语言实体**」，不是「立即数还是内存地址」。
**另外**：`const` ≠ 编译期常量，那是 `constexpr`。

### 1.2 `sizeof/README.md` —— 「编译器会重排成员」不存在

**原文**（`geninhe.cpp` 的注释）

> ```cpp
> /**
>  * @brief 此时B按照顺序：char a / int b / short a / long b
>  * 根据字节对齐 4+4+8+8=24
>  * 或编译器优化  char a / short a / int b / long b
>  * 根据字节对齐 2+2+4+8=16
>  */
> cout<<sizeof(B)<<endl; // 16 或 24
> ```

**实测**：

```bash
cat > sz.cpp <<'EOF'
#include <cstdio>
#include <cstddef>
class A { public: char a; int b; };
class B : A { public: short a; long b; };
int main(){
  std::printf("sizeof(A)=%zu sizeof(B)=%zu\n", sizeof(A), sizeof(B));
  std::printf("A::b off=%zu  B::a off=%zu  B::b off=%zu\n",
              offsetof(A,b), offsetof(B,a), offsetof(B,b));
}
EOF
g++ -std=c++17 -w sz.cpp -o sz && ./sz
```

```text
sizeof(A)=8 sizeof(B)=24
A::b off=4  B::a off=8  B::b off=16     ← 严格按声明顺序，没有重排
```

**✅ 正确说法**：

- 标准保证**同一访问控制段内**成员按声明顺序布局（不同访问控制段理论上允许重排）。
- **Itanium ABI 承诺按声明顺序**，g++ / clang 实测都不重排；MSVC 也不重排。
- 「16 或 24」这种写法最有害：它把「我不确定」包装成「编译器可能这样」，读者会以为布局不可预测。

### 1.3 `sizeof/README.md` —— 「多继承只有一个 vptr」错

**原文**：

> 「虚函数继承，**不管是单继承还是多继承**，都是继承了基类的 vptr。」

**实测**：

```bash
cat > ma.cpp <<'EOF'
#include <cstdio>
class VA { virtual void fun() {} };
class VB { virtual void fun2() {} };
class MA : public VA, public VB { };
int main(){ std::printf("sizeof(VA)=%zu sizeof(VB)=%zu sizeof(MA)=%zu\n",
                        sizeof(VA), sizeof(VB), sizeof(MA)); }
EOF
g++ -std=c++17 ma.cpp -o ma && ./ma
g++ -std=c++17 -c ma.cpp -o /dev/null -fdump-lang-class=-
```

```text
sizeof(VA)=8 sizeof(VB)=8 sizeof(MA)=16      ← 16 = 2 个 vptr

Vtable for MA: 6 entries
  0   (int (*)(...))0
  8   (int (*)(...))(& _ZTI2MA)
 16   (int (*)(...))VA::fun        ← 第一张子虚表（偏移 0）
 24   (int (*)(...))-8
 32   (int (*)(...))(& _ZTI2MA)
 40   (int (*)(...))VB::fun2       ← 第二张子虚表（偏移 -8）
```

**同一个 README 的「原则6」自己说「派生类虚继承多个虚函数，会继承所有虚函数的 vptr」，前后直接矛盾。**

**✅ 正确说法**：

> **多态对象里 vptr 的个数 = 它包含的多态基类子对象的个数。**

并且「**继承 vptr**」这个说法本身就不对：vptr 不是从基类继承来的，是**每个多态对象在构造时被写入指向自己的虚表的指针**。

**顺带一个仓库完全漏掉、但在 CAE/EDA 里天天用的定理**（空基类优化 EBO）：

```text
sizeof(Empty)  = 1
sizeof(struct EBO : Empty { int x; })   = 4    ← 空"基类"可被优化成 0 字节
sizeof(struct NoEBO { Empty e; int x; }) = 8   ← 空"成员"最小 1 字节 + 填充
```

**基类子对象可以是 0 字节，成员子对象最小 1 字节。** 这一条解释了 `compressed_pair`、`std::vector` 的 allocator 存储等一大堆库设计。

### 1.4 `inline/README.md` —— 把 `inline` 的真正语义搞错了（⭐ 最值得记住的一条）

**原文**：

> 「inline 能提高函数效率……编译器对 inline 函数的处理步骤：将 inline 函数体复制到 inline 函数调用点处；为所用 inline 函数中的局部变量分配内存空间；将 inline 函数的的输入参数和返回值映射到调用方法的局部变量空间中；如果 inline 函数有多个返回点，将其转变为 inline 函数代码块末尾的分支（使用 GOTO）。」

这是**教科书玩具模型**，不是真实编译器行为。而且它完全漏掉了 `inline` 的真正语义。

**实测 ①：`inline` 的真正作用是放宽 ODR**

```bash
printf 'int add(int a,int b){ return a+b; }\n' > h.h
printf '#include "h.h"\nint x(){return add(1,2);}\n' > a.cpp
printf '#include "h.h"\nint y(){return add(3,4);}\n' > b.cpp
printf 'int x(); int y(); int main(){return x()+y();}\n' > m.cpp

g++ -std=c++17 a.cpp b.cpp m.cpp -o m
#   → multiple definition of `add(int, int)'        ❌

sed -i 's/^int add/inline int add/' h.h
g++ -std=c++17 a.cpp b.cpp m.cpp -o m && echo OK
#   → OK                                            ✅
```

**实测 ②：链接层面的机械真相 —— 弱符号**：

```bash
g++ -std=c++17 -c a.cpp -o a.o && g++ -std=c++17 -c b.cpp -o b.o && nm -C a.o b.o
```

```text
a.o:                                  b.o:
0000000000000000 T x()                0000000000000000 T y()
0000000000000000 W add(int, int)      0000000000000000 W add(int, int)
                 ↑ 弱符号                                ↑ 完全相同的弱符号
```

**两个 `.o` 里有同名弱符号 `W` ⟹ 链接器默默合并成一份。**
**普通函数是强符号 `T`，出现两份就 `multiple definition`。**

**实测 ③：`inline` 关键字与「内联」无关**

```bash
cat > ni.cpp <<'EOF'
int __attribute__((noinline)) sq_noinline(int x){ return x*x; }
int sq_plain(int x){ return x*x; }   // 没有写 inline
int f(int x){ return sq_plain(x); }
int g(int x){ return sq_noinline(x); }
EOF
g++ -std=c++17 -O2 -S ni.cpp -o - | grep -A 4 -E '^_Z1fi:|^_Z1gi:'
```

```text
_Z1fi:                          _Z1gi:
    imull %edi, %edi                jmp _Z11sq_noinlinei
    movl  %edi, %eax            ← 没内联
    ret                     ← 完全内联！但没写 inline
```

**✅ 正确说法**：

> **`inline` 的主职是「告诉链接器：这个符号允许多份定义，随便挑一份」（放宽 ODR）。**
> 至于内不内联，**完全由优化器自己决定**——未写 `inline` 的函数在 `-O2` 下照样被内联。

**这条的推论极其重要**（仓库完全没有）：

| 能放头文件？ | 依据 |
| --- | --- |
| 类内定义的成员函数 | ✅ 隐式 `inline` |
| 模板函数 / 类模板成员函数 | ✅ 模板实例**隐式** `inline`（实测 `W`） |
| `constexpr` 函数 | ✅ 隐式 `inline`（实测 `W`） |
| C++17 `inline` 变量 / `static inline` | ✅ |
| **普通函数定义 / 普通全局变量定义** | ❌ 强符号 ⟹ `multiple definition` |

**这就是「为什么模板必须 header-only」的答案。**

### 1.5 `volatile/README.md` —— 把 `volatile` 当成线程同步工具（⚠️ 最危险的一条）

**原文**：

> 「（3）多线程应用中被多个任务共享的变量。当多个线程共享某一个变量时，该变量的值会被某一个线程更改，应该用 `volatile` 声明。……加上 `volatile`，程序在执行时，每次均从内存中读出 `bStop` 的值，就不会死循环了。」

并给了这个例子：

```cpp
volatile bool bStop = false;
void threadFunc1() { while(!bStop){...} }        // 线程 1
void threadFunc2() { bStop = true; }             // 线程 2
```

**❌ 这是错的，而且错得危险。**

**✅ 正确说法**：

> **`volatile` 不是同步机制。它不提供原子性，也不提供内存序（memory ordering）。**

| `volatile` 保证 | `volatile` **不**保证 |
| --- | --- |
| 编译器不会把这次访问合并/删除 | **原子性**（读-改-写不是原子的） |
| 每次访问都真的读写内存 | **内存序**（不阻止 CPU / 编译器重排） |
| 用于内存映射 I/O、`setjmp` 局部变量、`sig_atomic_t` | **data race 仍然发生 ⟹ 仍然是 UB** |

上面的例子：

- 在 C++ 内存模型下，两个线程无同步地访问 `bStop`、其中一个是写 ⟹ **data race**，**C++11 起这是 UB**（不是「可能读到旧值」）。
- 即使 `volatile` 让编译器每次都从内存读，**CPU 层面仍然可能重排**，编译器也可能把循环外的其他操作移进循环。

**正确做法**：用 `std::atomic<bool>`

```cpp
#include <atomic>
std::atomic<bool> bStop{false};
void threadFunc1() { while(!bStop.load(std::memory_order_acquire)){...} }
void threadFunc2() { bStop.store(true, std::memory_order_release); }
```

**同一篇里的另一处**：`int *output = (unsigned int *)0xff800000;` —— **这行本身就编译不过**

```text
$ g++ -std=c++17 -fsyntax-only vol1.cpp
error: invalid conversion from 'unsigned int*' to 'int*' [-fpermissive]
```

（应为 `unsigned int *output = ...`）

### 1.6 `decltype/README.md` —— `decltype(1)` 与 `decltype(Func(1))` 的类型写错了

**原文**：

```cpp
decltype(1) var12;      // 注释说：const int
decltype(Func(1)) var13 = true;   // 注释说：const bool
decltype("hello") var11 = "hello";  // 注释说：const char(&)[9]
```

**实测**：

```bash
cat > dt.cpp <<'EOF'
#include <type_traits>
static_assert(std::is_same_v<decltype(1), int>, "decltype(1) 是 int");
static_assert(std::is_same_v<decltype("hello"), const char(&)[6]>, "长度是 6 不是 9");
const bool Func(int);
static_assert(std::is_same_v<decltype(Func(1)), bool>, "C++17 起是 bool");
int main(){}
EOF
g++ -std=c++17 -fsyntax-only dt.cpp && echo 全部通过
```

| 仓库写法 | 实测 |
| --- | --- |
| `decltype(1)` = `const int` | ❌ 是 **`int`**（字面量是纯右值，无 cv） |
| `decltype("hello")` = `const char(&)[9]` | ❌ 是 **`const char(&)[6]`**（`"hello"` 是 5 个字符 + `\0`） |
| `decltype(Func(1))` = `const bool` | ❌ 在现代编译器上是 **`bool`** |

**关于第三条（有意思的标准演进）**：

```text
g++      c++14  → bool        clang++  c++14  → bool
g++      c++17  → bool        clang++  c++17  → bool
g++      c++20  → bool        clang++  c++20  → bool
```

C++17 规定**纯右值会剥掉 cv 限定**，而 GCC/Clang 把这条规则作为缺陷修复**回溯应用到了所有标准模式**。所以仓库的说法在**现代编译器上任何 `-std` 下都不成立**。

**同一篇里的代码缺陷**：

```cpp
typedef decltype(vec.begin()) vectype;
for (vectype i = vec.begin; i != vec.end; i++)   // ❌ 少了两对括号
```

应该是 `vec.begin()` / `vec.end()`。**代码照抄编译不过。**

**同一篇里的拼写**：`decltype(s.d) var3;//doubel` （应为 `double`）。

**仓库漏掉的重点**：`decltype(auto)`（C++14）和 `decltype(x)` vs `decltype((x))` 的差别（前者给「实体的类型」，后者给「表达式 `(x)` 的类型」= 引用）。

### 1.7 `bit/README.md` —— 示例代码有拼写错误，且推荐了 UB 做法

**① 代码拼写错误，照抄编译不过**：

```cpp
struct _PRCODE {
    unsigned int code1: 2;
    unsigned int cdde2: 2;    // ← 字段名是 cdde2
    unsigned int code3: 8;
};
prcode.code1 = 0;
prcode.code2 = 3;             // ← 却用 code2（不存在）
procde.code3 = 102;           // ← 又拼成 procde
```

两处错误：`code2`（应为 `cdde2`）、`procde`（应为 `prcode`）。

**② 类型表与上面的说明自相矛盾**：

| 位置 | 说法 |
|---|---|
| 正文 | 「位域的类型必须是**整型或枚举类型**」 ✅ |
| 表格 | 「type 必须为 **int、signed int 或者 unsigned int** 类型」 ❌ |

**✅ 正确说法**：任何整型或枚举类型都可以（含 `char`、`short`、`long`、`long long`、`bool`、`enum class`）。

**③ 推荐的「重映射」是 UB**：

```cpp
int* p = (int *) &b1;
*p = 0;                       // ❌ 违反 strict aliasing ⟹ UB
```

```cpp
union u_box { struct box st_box; unsigned int ui_box; };
union u_box u;
u.ui_box = 0;                 // 用 union 做类型双关
```

**✅ 正确说法**：

- **在 C++ 里通过 union 做类型双关（写一个成员、读另一个）是 UB**（C 里合法，这是 C/C++ 又一个关键区别）。
- 清零应该用 `memset(&b1, 0, sizeof b1)`，或者直接逐个成员赋值。
- 类型双关的正规手段：`std::memcpy`，或 C++20 的 `std::bit_cast`。

**④ 位域这一篇的 `sizeof` 数值全对**（这点要给它记一分）

```text
box(1+3+4 bits)      = 4     ✅ README 说 = sizeof(unsigned int)
stuffA(30+4+3)       = 8     ✅ README 说 8
stuffB(30+:2+4+:0+3) = 12    ✅ README 说 12
bit.cpp 实际输出      = 1 3 5 12  ✅
```

## 2 · 🟡 过时说法（当时对，现在不成立）

| 位置 | 原文 | 现状 |
| --- | --- | --- |
| `enum/README.md` | 「应该用**类中的枚举常量**来实现类的常量」 | C++98 的权宜之计。**C++11 起用 `static constexpr int SIZE = 100;`**，语义更清楚（枚举只能装整数，`constexpr` 可以是任何字面量类型） |
| `enum/README.md` | `const int SIZE = 100; int array[SIZE];` 标为「(c++11标准前) 错误」 | C++11 之后**依然错**，但错因变了：NSDMI 允许了，可 `SIZE` 在类体内**不是常量表达式**。仓库用括号一笔带过，容易误导 |
| `const/README.md` | 「在 C++ 中，static 静态成员变量不能在类的内部初始化」 | `static const int` / `constexpr` 可以（C++11），`static inline` 可以（C++17）。实测：`static int y = 3;` 在 C++11 报 `ISO C++ forbids in-class initialization of non-const static member` ✅，但 `static const int k = 7;` 通过 |
| `extern/README.md` | 「C 的话则会是形如 `_add`」 | 那是 **macOS / Mach-O** 风格。**Linux / ELF 下不加下划线**，就是 `add` |
| `virtual/README.md` | 「只要一个类有可能会被其它类所继承，就应该声明虚析构函数(哪怕该析构函数不执行任何操作)」 | **过于绝对**，且漏掉现代关键点：① 只有**打算通过基类指针 delete** 时才需要；② 设计成「不该被多态删除」的基类应该用 **protected 非虚析构**；③ **声明虚析构会隐式删除移动操作**（需要显式 `= default` 找回）——这是真实代码里高频的静默性能退化 |
| `decltype/README.md` | `decltype(1)` = `const int`、`decltype(Func(1))` = `const bool` | 见 §1.6。C++17 起纯右值剥掉 cv 限定，现代编译器回溯应用到所有 `-std` |
| `abstract/README.md` | 「纯虚函数：没有函数体的虚函数」 | **不准确**：纯虚函数**可以有函数体**（类外定义），只是不能通过虚派发调用它（构造/析构里的显式限定调用可以） |

## 3 · 🟠 结论对、推理错（最危险的一类）

> 这类最难发现，因为「验证结论」会通过，但**推理错了，遇到变体就翻车**。

### 3.1 `virtual/README.md` + `inline/README.md` —— 虚函数能否内联的判据错了

**原文**：

> 「`inline virtual` 唯一可以内联的时候是：编译器知道所调用的对象是哪个类。**这只有在编译器具有实际对象而不是对象的指针或引用时才会发生**。」

**反例（实测）**：

```cpp
struct Base { virtual int f() const { return 1; } virtual ~Base() = default; };
struct Sealed final : Base { int f() const override { return 3; } };
int call_final(Sealed& s) { return s.f(); }   // 参数是"引用"！
```

```asm
call_final(Sealed&):
    movl $3, %eax          ← 完全消除
    ret
```

**参数明明是引用**，照样被完全消除，因为 `final` 让编译器**证明了**动态类型。

**✅ 正确说法**：

> 判据是「**编译器能否证明动态类型**」，不是「有没有实际对象」。
> 证明来源：① 实际对象（`Derived d; d.f()`）；② `final`；③ LTO；④ 推测去虚化（先猜，猜错再跳，实测 `call_direct` 就是这个形态）。

### 3.2 `pointer_refer/README.md` —— 用 `-O0` 汇编证明「没有性能差距」

**原文**：

> 「我们发现 test2 对应的汇编代码和 test1 对应的汇编代码完全相同，这说明……引用只是 C++ 对指针操作的一个『语法糖』……不用担心两者的性能差距。」

**问题：实验设计错了。** `-O0` 下编译器不做优化，任何两个语义等价的函数都会生成相同（且臃肿）的代码。**`-O0` 的汇编不能作为任何性能结论的证据。**

**✅ 正确说法**：

- 标准**不要求**引用用指针实现。内联后，引用可能**完全不物化任何存储**。
- 真正的差别在**语义**：别名（非独立身份）、必须初始化、不可重绑定、非空保证。
- 性能上：`-O2` 下两者通常无差别；但语义差异会决定**优化器能否做某些推理**（如「这个引用不能重绑定」）。

**同篇还有两处**：

- `if(p != null_ptr)` —— **拼写错误**，应为 `nullptr`（`null_ptr` 不存在）。
- 漏掉了最实用的规则 —— **临时对象生命周期延长的精确边界**（见 `01` 的 T3）。

### 3.3 `this/README.md` —— 结论对，但两个关键说法有偏差

**结论部分完全正确**（值得肯定）：非 const 成员函数里 `this` 是 `A* const`，const 成员函数里是 `const A* const`。

**但**：

| 原文 | 问题 |
| --- | --- |
| 「this 在成员函数的开始执行前**构造**，在成员的执行结束后**清除**」 | `this` **不是对象**，它是**隐含参数**（一个指针类型的纯右值）。不存在「构造/清除」。这个措辞会让你以后看汇编时对不上号 |
| `Person(char *n, ...)` 用字符串字面量调用 | 实测 g++：`warning: ISO C++ forbids converting a string constant to 'char*'`；clang++：`warning: ISO C++11 does not allow conversion from string literal to 'char *'`。**两个编译器都只告警不报错**（为兼容老代码），但**都是不合法代码** |
| 「类和结构只有一个区别」 | 不完整：还有**默认继承访问权限**（`struct` public / `class` private） |

**漏掉的重点**：`const` 成员函数的机制**正是 `mutable` 存在的唯一理由**。

### 3.4 `extern/README.md` —— 报错输出是伪造的

**原文**：

```text
> g++ add.cpp add.o -o main
add.o：在函数‘main’中：              ← ❌ add.o 里根本没有 main
add.cpp:(.text+0x0): `main'被多次定义      ← ❌ 与现象无关
/tmp/ccH65yQF.o:add.cpp:(.text+0x0)：第一次在此定义
/tmp/ccH65yQF.o：在函数‘main’中：
add.cpp:(.text+0xf)：对‘add(int, int)’未定义的引用
```

**前半段明显是从别处串味拼凑的**（`add.o` 里没有 `main`）。只有最后一句「未定义的引用」是对的。

**✅ 真实报错**就是一句：

```text
undefined reference to `add(int, int)'
```

因为 C++ 里生成的符号是 `_Z3addii`，而 C 生成的符号是 `add`。

### 3.5 `macro/README.md` —— `##` 与 `\` 的规则不准

| 原文 | 实测 |
| --- | --- |
| 「如果 `##` 后的参数本身也是一个宏的话，`##` 会阻止这个宏的展开」 | **不准确**。`##` 只阻止**操作数在粘贴前**的展开，**粘贴结果会被重新扫描并展开**。实测：`#define CAT(a,b) a##b` + `CAT(hello,_tok)` → 输出 `from hello_tok`（宏被展开了） |
| 「注意 `\` **前**留空格」 | **应反过来**：`\` **后面不能有任何字符**（空格/注释都不行）。实测 `\` 后带空格 → `warning: backslash and newline separated by space` |

**实测脚本**：

```bash
cat > pp.cpp <<'EOF'
#include <cstdio>
#define STR(x)   #x
#define XSTR(x)  STR(x)
#define NAME hello
#define hello_tok "from hello_tok"
#define CAT(a,b) a##b
int main(){
  puts(STR(NAME));        // 不做宏展开 → "NAME"
  puts(XSTR(NAME));       // 两级间接 → "hello"
  puts(CAT(hello,_tok));  // 粘贴结果被重新扫描 → 宏展开
}
EOF
g++ -std=c++17 pp.cpp -o pp && ./pp
```

```text
NAME
hello
from hello_tok      ← 证明 ## 的结果会被展开
```

**漏掉的重点**：`#` 字符串化**不做宏展开**，所以才有经典的两级技巧（`STR` / `XSTR`）。
