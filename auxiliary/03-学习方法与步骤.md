# 03 · 学习方法与步骤

> `01` 给了你「世界是怎样的」，本文件给你「**怎么把它变成自己的判断力**」。
>
> 核心内容：**六步实证法** · **三轮阅读法** · **「什么算掌握了」的判定标准** · **面向审 AI 代码的分层检查流程**

---

## 一、总思路：为什么不能"读懂"就算学会

C++ 有一个特点：**它的规则看起来都能"看懂"，但遇到变体就完全不确定。**

原因在于仓库那种「主题 → 结论 → 代码」的写法只给了你**结论**，没给它**成立的边界条件**。而工程中的代码，写的正好都是边界。

举一个真实例子（来自本目录的实测）：

> 仓库说：「虚函数表现多态性的时候不能内联，只有在编译器具有**实际对象**而不是**指针或引用**时才会发生。」

这句话读完你「懂了」。但下面这段代码你就判断不了了：

```cpp
struct Sealed final : Base { int f() const override { return 3; } };
int call_final(Sealed& s) { return s.f(); }   // 参数是引用 —— 那到底会不会内联？
```

**实测答案：会，而且是完全消除（`movl $3, %eax`）。**
因为「是否有实际对象」不是真正的判据，**「编译器能否证明动态类型」**才是。`final` 就是一个证明。

> **结论**：只有「能判断**变体**」才算掌握。判断力的来源只有两个 —— **底层原理**（`01`）+ **亲手实测**（本文件）。

## 二、六步实证法（核心方法）

对仓库里**每一个**你想掌握的主题，走这六步。一个主题约 15~30 分钟。

```text
① 定位  →  ② 预测  →  ③ 实测  →  ④ 对账  →  ⑤ 反例  →  ⑥ 归档
   ↑                                                        │
   └────────────── 骨架（01）+ 尺子（02）←───────────────────┘
```

### ① 定位 —— 先查框架，**不要先看代码**

打开 `01-知识框架.md`，回答：**这个主题挂在哪条公理/定理上？**

| 主题 | 应能立刻定位到 |
| --- | --- |
| `extern` / `static` / `inline` | **A1** 翻译单元公理 |
| `sizeof` / `union` / `bit` | **A3** 对象模型公理（存储） |
| `virtual` / `vptr_vtable` / `abstract` | **A3**（类型）+ **A4**（分层）+ **T5**（分派） |
| `const` / `volatile` | **T1** cv 是类型属性 |
| RAII / 智能指针 / `copy-swap` | **A5** + **T4** |
| 移动语义 / 完美转发 / `decltype` | **T7** + **T4** |

**如果定位不出来，说明框架没读懂 —— 回到 `01`，不要往下走。**

> **为什么这一步必须在最前**：定位决定了你会用哪一套原理解释接下来的所有现象。先看代码，你的解释会变成「凑」出来的。

### ② 预测 —— 在读仓库解释**之前**，先写下你的答案

这是本方法里**最关键、最容易被跳过**的一步。它的作用是造一个**可被证伪的预期**。

具体做法：只读仓库的**代码**（`.cpp` 文件），**遮住 README 的解释段落**，在纸上写下：

1. 这段代码**会不会编译通过**？
2. **会输出什么**？
3. **`sizeof` / 偏移 / 汇编会是什么**？

> 心理学上这叫「**生成效应**」：你先自己生成一个答案，哪怕错了，后续的修正也会记得极牢。而直接读答案，只会产生「我懂了」的错觉。

### ③ 实测 —— 打开 `05-实验工具箱.md`，跑它

不是"看"，是"跑"。每一条结论都要有**你自己终端里的真实输出**。

最低要求（按主题类型选）：

| 主题类型 | 必须做的实测 |
| --- | --- |
| 涉及编译/链接 | 编两遍：`-O0` 和 `-O2`；看 `nm` 的符号类型 |
| 涉及布局 / `sizeof` | `sizeof` + `offsetof` 打印；`-fdump-lang-class=-` |
| 涉及虚函数 / 性能 | `-O2 -S` 看汇编；确认是 `jmp *(%rax)` 还是直接 `movl $N, %eax` |
| 涉及 UB | 加 `-fsanitize=address,undefined`，看是否报错 |
| 涉及并发 | 加 `-fsanitize=thread`；把线程数加大重跑 |

**一条铁律**：`-O0` 的汇编**不能**作为性能结论的证据。仓库 `pointer_refer/README.md` 就是拿 `-O0` 的汇编得出「引用和指针完全一样、没有性能差距」的结论——那个实验设计本身就是错的。

### ④ 对账 —— 把「你的实测」和「仓库的解释」摆在一起

找出**三类差异**，它们就是你的收获：

| 差异类型 | 含义 | 处理 |
| --- | --- | --- |
| **完全一致** | 仓库是对的 | 快速过。记下「已验证」记号 |
| **结论对、推理错** | ⚠️ 最危险的一类 | **重点记**。推理错了，变体必翻车 |
| **结论错** | 仓库是错的 | 记入你的笔记，并对照 `06-仓库审计报告.md` 看是否已收录 |

**判断「推理错」的方法**：把仓库的解释**当成一个可证伪的预测**，构造一个它预测不到的情况：
> 仓库说「只能在有实际对象时内联」⟹ 预测：**用引用参数一定不内联** ⟹ 实测 `call_final(Sealed&)` ⟹ **预测失败** ⟹ 推理错。

### ⑤ 反例 —— 构造一个仓库里**没有**的变体

**这一步是「知识」和「能力」的分界线。**

做法：把仓库代码改动**一处**，让原来的结论**不再成立**（或换一种方式成立）。例如：

| 仓库主题 | 你可以构造的反例 |
| --- | --- |
| `inline` 可以放头文件 | 把函数改成一个**全局变量**放头文件 → 会不会报错？ |
| `static const int` 类内初始化 | 加一行 `&A::k` 取地址 → 会发生什么？ |
| 模板必须 header-only | 真把模板定义放 `.cpp` 会报什么错？能通过显式实例化救回来吗？ |
| `virtual` 有运行期成本 | 给类加 `final` → 汇编变了吗？ |

> **构造不出来的，就是没掌握。** 返回到 ①。

### ⑥ 归档 —— 留下三行笔记

```markdown
## 主题：<名字>                      [对应：A1 / T6]
- 原则：<一句话>
- 前提：<这条原则在什么条件下不成立>      ← 最重要的一行
- 反例：<我自己构造的、仓库里没有的失败案例>
```

**第三行是硬要求。** 没有反例的主题，一个月后你只会记得「好像有个规则」，遇到变体还是会犹豫。

## 三、三轮阅读法（怎么安排这 95 篇的阅读节奏）

不要从头到尾线性读——那会得到 95 个孤立印象。

### 第一轮 · 骨架轮（约 40 分钟，**不碰仓库代码**）

| 做什么 | 产物 |
| --- | --- |
| 通读 `01-知识框架.md` | 能凭记忆画出「公理 → 定理」的树 |
| 背 `02` 的表 1（三把尺子）、表 2（对象四元组） | 能默写 |
| 读一遍本文件 | 记住六步法的六个字：**定位 预测 实测 对账 反例 归档** |

**验收**：给你仓库里任意一篇「那些事」的标题，你能说出它挂在哪条公理/定理上。

### 第二轮 · 对账轮（每主题 15~30 分钟）

按**你自己的需求**排序，不按仓库目录顺序。推荐优先级：

1. **先把 `06-仓库审计报告.md` 读一遍** —— 别人踩过的坑，成本最低的收获
2. 你实际代码里遇到过的痛点（编译不过、链接不过、`-O0/-O2` 不一致、性能不对）
3. `01` 里标注为「高频」的主题：A1 相关的（`extern`/`static`/`inline`）、T5（`virtual`）、T4（移动/拷贝）

对每一篇：走六步法。

### 第三轮 · 构造轮（按 `04-学习路线图.md` 的 14 课走）

不再按仓库目录组织，改按**公理和定理**组织。每一课都要求你**独立构造一个反例**。

**验收**：14 课的「构造」检查点全部能通过。

## 四、「什么算掌握了」—— 三层判定标准

对任何一个知识点，用力问**三类问题**。三关都过 = 掌握。

### 第 1 层 · 判定（能不能看懂）

> **给一段代码，你能说出它会不会编译/链接通过、运行输出什么？**

例：「这个头文件里定义了 `int add(int,int){...}`，被两个 `.cpp` 包含，会怎样？」
→ 能回答「`multiple definition`，因为它是强符号 `T`，不是 `inline`」。

### 第 2 层 · 预测（能不能预判变体）

> **改动一处，你能预判结果会不会变？**

例：「给那个函数加上 `inline` 呢？」→ 「链接通过。`inline` 让符号变成弱符号 `W`，链接器合并。」
例：「那如果把 `inline` 改成 `static` 呢？」→ 「也能通过，但语义不同：`static` 是每个 TU 各留一份**独立的**副本（地址不同），`inline` 是合并成**同一份**。」

### 第 3 层 · 构造（能不能设计验证）

> **你能自己设计一个实验，把这条规则**从零**验证出来吗？给你一个陌生的说法，你能判断真伪吗？**

例：「有人说 `const` 变量在内存中只有一份拷贝，你怎么验证？」
→ 「在两个 TU 里各定义 `const int c`（值不同），如果链接通过且各用各的值，说明是内部链接、每个 TU 一份。完成。」

**这三层就是 `04-学习路线图.md` 里每课的三个检查点。**

## 五、面向「审查 AI 生成代码」的分层检查流程

这个方法是为你的**实际目标**设计的。拿到一段 AI 生成的 C++ 代码，**按这个顺序**看，成本从低到高：

### 第 0 层 · 让工具先看（30 秒，永远先做这个）

```bash
# 最高警告等级 + 语法检查
g++ -std=c++20 -Wall -Wextra -Wpedantic -Wshadow -Wconversion -fsyntax-only file.cpp

# 链接 + ODR 检查（-flto 才能让编译器跨 TU 检查 ODR）
g++ -std=c++20 -O2 -flto -Wodr *.cpp -o prog

# 运行时 UB 检查
g++ -std=c++20 -g -O1 -fsanitize=address,undefined -fno-omit-frame-pointer *.cpp -o prog && ./prog
```

> **AI 生成的代码最常见的三类问题，第 0 层就能抓出一大半**：警告、ODR、UB。

### 第 1 层 · 看「约束有没有写进类型里」（元原则 2）

| 检查 | 症状 |
| --- | --- |
| 单参构造函数有没有 `explicit`？ | 没有 ⟹ 存在隐式转换的意外路径 |
| 覆写虚函数有没有 `override`？ | 没有 ⟹ 签名写错时会**悄悄不覆写**（最阴） |
| 枚举用 `enum` 还是 `enum class`？ | `enum` ⟹ 会隐式转 `int`，可跨枚举比较 |
| 移动/拷贝是否被意外 `delete`？ | 声明了析构 ⟹ 移动**隐式被删除**，代码会悄悄退回拷贝 |
| `const`-correctness 是否完整？ | 成员函数该 const 却没写 ⟹ 调用方到处要 `const_cast` |

### 第 2 层 · 用对象四元组定位（A3 + 表 2）

**逐个成员问**：它的**存储/生命周期/类型/值**分别是什么？

- 有裸 `new` 吗？谁 `delete`？**（生命周期）**
- 有裸指针成员吗？它**借用**还是**拥有**？**（所有权）**
- 函数返回引用/指针吗？指向的东西能活过调用吗？**（T3 悬垂）**
- 基类指针上有 `delete` 吗？基类析构是虚的吗？**（T5）**
- 类之间的关系是**值语义**还是**引用语义**？拷贝会不会意外共享内部状态？**（T4）**

### 第 3 层 · 用值类别看「移动/转发」是否正确（T4 + T7）

- 有 `std::move` 用在 `const` 对象上吗？→ **无效**（变成拷贝），典型的「写了等于没写」
- 移动构造函数里接管了资源后，源对象被置成安全状态了吗？
- `std::forward` 用在了**非转发引用**上吗？→ 那是 bug
- 返回局部变量时写了 `std::move` 吗？→ **会阻止 NRVO**，反而更慢

### 第 4 层 · 用 A2 找 UB（最终防线）

```bash
g++ -fsanitize=address,undefined -O1 -g ...
```

重点盯：`vector::operator[]` 越界、有符号溢出、`reinterpret_cast` 类型双关、未初始化读、数据竞争。

### 第 5 层 · 用元原则 3 看「有没有把编译期的事丢到运行期」

- 运行期的 `switch` 在判断一个编译期已知的类型？→ 应该用模板 / `if constexpr`
- 运行期算常量表？→ 应该 `constexpr`
- 用虚函数实现一个**编译期就固定**的分派？→ 应该用静态多态（T5）

### 输出格式建议

```markdown
## 审查报告：<文件名>
### 会崩溃 / 有 UB（必须改）
1. <位置> — <哪一元组/哪条公理> — <具体问题> — <修法>
### 语义隐患（应该改）
...
### 风格 / 可读性（可选）
...
### 已确认正确的部分
...
```

**最后一段「已确认正确的部分」不要省** —— 它防止你把「我没看懂」误报成「它是错的」。

## 六、提问模板（用这个来问我，效率最高）

当你带着一个问题来问我时，按这个结构给我：

```text
【主题】<仓库里哪一篇 / 哪条公理定理>
【我的预测】<我预测会……>
【我的实测】<我跑了什么命令，看到什么>
【冲突点】<实测和仓库/我的预测不一致的地方>
【我的理解】<我目前的解释是……>
```

**为什么这样最有效**：它把「我不知道」变成了「我预测 A，实测是 B」。
后者我可以**一句话指出你框架里的哪一步错了**；前者我只能重讲一遍你已经看过的内容。
