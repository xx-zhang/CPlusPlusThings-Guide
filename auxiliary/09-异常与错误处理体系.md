# 09 · 异常与错误处理体系

## 0 · 这个体系解决什么问题

AI 生成的代码里错误处理最常见的四个形态（也是你审查时最先看到的）：

```cpp
// 形态1：return false + 全局标志（上下文全丢）
bool ok = solver.compute();            // ？到底哪一步失败了
// 形态2：错误路径淹没主逻辑
if (!check1()) return -1;  if (!check2()) return -2;  ...  // 主逻辑被 if 淹了
// 形态3：静默吞错
catch (...) {}                          // ← 调试黑洞
// 形态4：用返回值当"异常"传了十层
```

本体系给你一套**可判定**的策略：什么错用异常、什么错用错误码、什么错该直接断言，以及怎么写才异常安全。

## 1 · 核心原则（全部是公理的必然结果）

### 1.1 异常的传播路径 = 析构的调用路径（A5 的直接推论）

栈展开时**所有已构造局部对象的析构函数必被调用**，然后异常沿调用栈向上传播。所以：

- **为什么 C++ 不需要 `finally`**：析构函数就是被编译器强制的 `finally`。
- **为什么析构函数不能抛异常**：析构在栈展开中可能被调用，此时再抛 ⟹ 两个活跃异常 ⟹ `std::terminate`。**实测**（08 已录）：`terminate called`；g++ 还提示「C++11 起析构默认 noexcept」。

### 1.2 `noexcept` 是接口契约的一部分——和 const 同构（T1 + T4 交叉）

> `const` 说「我不会改你」；`noexcept` 说「我不会在失败时抛给你」。两者都是**类型层面的接口承诺**，不是注释。

`noexcept` 的实际影响（不只是文档）：

- **容器选移动还是拷贝**（T4）：`std::vector` 扩容时，如果移动构造 `noexcept` 就用移动（O(1) 偷），否则退回拷贝（O(n) 复制）。**实测**（08 已录）：`noexcept move` → 15 次移动 0 复制；copy-only → 15 次复制。
- **`swap` 必须 `noexcept`**：这是 copy-swap、标准库容器的前提。
- **契约破裂**：`noexcept` 函数抛 ⟹ `terminate`（不是"漏给调用者处理"）。**实测**（08 已录）。

### 1.3 错误分两类，处理工具不同（决策的第一刀）

| 错误类型 | 特征 | 工具 |
| --- | --- | --- |
| **预期错误**（expected） | 调用者**本来就知道可能失败**、需要在局部处理：文件不存在、输入非法、网络超时 | 错误码 / `std::optional` / **C++23 `std::expected`**；热路径里尤其要避免异常 |
| **异常错误**（exceptional） | 调用者**无法在局部合理处理**、需要跨多层传播：内存耗尽、不变量破坏、库的底层故障 | 异常（throw） |

**判据**：你能在调用点给用户一个「怎么办」吗？能 → 预期错误；不能（或要穿 5 层才能办）→ 异常。

### 1.4 异常安全三级（背下来，写任何改动前先问自己到哪一级）

```text
基本保证：出错后对象可用、不泄漏资源（但状态"未指定"）
强保证：  出错后对象回到操作前状态（像没发生过）——copy-swap 天然做到
不抛保证： 操作保证不抛（swap/移动/析构/noexcept 标记的东西）
```

**写容器/大对象的成员函数时，目标至少「强保证」；`swap`/`move`/析构必须「不抛」。**

## 2 · 知识点地图（离散点）

| 点 | 一句话关键 | 注意 |
| --- | --- | --- |
| `throw` 表达式 | 抛出的**是值，不是指针**；`throw;` 在原捕获内重新抛出，保持类型 | 裸 `throw new X` 是反模式 |
| `catch` 子句 | 按**异常对象的动态类型**匹配，匹配「声明类型」的可访问基类；`...` 兜底 | **按 const 引用捕获**（避免拷贝与切片） |
| 栈展开 | 构造完成的局部对象逆序析构；构造函数本身抛 ⟹ **已构造的成员会被析构** | 半构造的对象没有析构被调用（它不存在） |
| `noexcept` | 说明符（函数契约）与操作符（`noexcept(f(x))` 编译期查询）是两回事 | 用 `static_assert(noexcept(op))` 检查契约 |
| `terminate` | noexcept 内抛 / 栈展开中析构抛 ⟹ terminate | 想让它可观测，装 sigabrt handler 或 `std::set_terminate` |
| 异常安全三级 | 基本/强/不抛 | 见 1.4 |
| copy-swap | 拷贝到临时（失败则原对象不动）→ `swap`（noexcept）→ 天然强保证 | T4 |
| `std::exception` 层次 | `logic_error`（可预见）/`runtime_error`（运行环境） | 自定义异常应继承 `std::runtime_error` |
| `assert` vs `static_assert` | 前者运行时、`NDEBUG` 可关、**表达式必须无副作用**（`NDEBUG` 下副作用消失！）；后者编译期 | 断言的是「不可能发生」，不是「预期错误」 |

## 3 · 决策流程：这段代码的错误，到底怎么处理

```text
遇到一个可能失败的操作
 │ Q1 失败是"预期"的吗？（调用者能在局部给出怎么办）
 ├─ 是 → Q2 在热路径/高频调用里吗？
 │       ├─ 是 → 错误码 / std::expected / std::optional（不抛异常）
 │       └─ 否 → 也可以用异常，但至少别吞掉
 └─ 否（异常错误，须跨层）→ throw（按值抛、按 const& 捕获）
        │ Q3 我用 RAII 把资源包好了吗？（锁/句柄/内存）
        │    └─ 否 → 先包 RAII 再折腾异常（否则栈展开时泄漏）
        └─ 捕获处：能给出"怎么办"就在这catch；否则继续向上
            └─ 最外层：打日志 + std::terminate/退出码（绝不空 catch 吞掉）
```

**写对象成员函数时的异常安全模板**：

```cpp
class BigData {
  std::vector<double> data_;
public:
  void reset_with(const std::vector<double>& v) {
    auto tmp = v;                 // 1. 拷贝到临时（失败=抛，原对象没动）
    data_.swap(tmp);              // 2. noexcept swap 提交    ⟹ 强保证
  }
};
```

## 4 · 常见坑（AI 代码高频，逐条对号入座）

| 坑 | 为什么是坑 | 修法 |
| --- | --- | --- |
| `catch(...){}` 空块 | 错误被吞 = 调试黑洞；数据已被污染还在继续跑 | 至少 `std::current_exception` 记录 + 打日志；顶层可 terminate |
| `catch (SomeError e)` 按值 | 复制 + **切片**（派生异常收到基类就会丢信息） | `catch (const SomeError& e)` |
| 析构里做会失败的事 | 析构 noexcept 且不能在栈展开中抛；失败只能吞或记录 | 析构只做「不会失败」的事；失败交给显式 `close()` |
| `new` 后不检查 | C++ 的 `new` 失败**抛 `bad_alloc`**，不返回 null（不同于 malloc 时代） | 要么 `try/catch` 要么 `nothrow` 版本；不写 `if(!p)` |
| 类没写 move 却往容器放 | 扩容全拷贝（实测 15 次拷贝） | 加 `noexcept` 移动构造/赋值，或 `swap`——见 T4/08 |
| 构造函数里抛 | 成员已构造的会被析构（好），但半构造对象没有析构（你控制不了） | 用 RAII 成员；不要在 ctor 里手动 new 多处 |
| `assert(expensive_call())` | `NDEBUG` 一开整个调用消失 | 断言里只放无副作用检查 |
| 用返回值传错误十层 | 每层都要 if 判断，主逻辑淹没 | 异常（或 expected）——见决策流程 |

struct S { std::vector<int> v; void swap(S& o) noexcept { v.swap(o.v); } };
static_assert(noexcept(std::declval<S>().swap(std::declval<S&>())), "swap 必须 noexcept");

## 6 · 与全局的连接

- **A2**：越界读**不保证崩溃**（08 反例：#0 帧之外它打印 2.0 正常退出）——**别指望崩溃来暴露错误**，错误路径要靠异常和显式检查。
- **A5**：异常传播路径 = 析构调用路径 ⟹ 所有"返回类错误码但忘了释放资源"的问题都该换成 RAII。
- **T4**：copy-swap 的强保证 = RAII + noexcept swap 的组合技。

## 7 · 自测三问

- **判定**：`struct X { ~X() { throw 1; } };` 在已有异常传播时析构，会发生什么？（terminate，为什么？）
