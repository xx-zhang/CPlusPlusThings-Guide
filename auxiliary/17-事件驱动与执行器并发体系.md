# 17 · 事件驱动与执行器并发体系

> **场景**：ROS2 的并发不是"你自己开线程"，而是「执行器调度回调」。回调里阻塞/长任务 ⟹ 饿死；回调里同步等结果 ⟹ 死锁。不懂这个模型，写出的节点"偶尔卡死"。
> **挂靠**：A2（data race 判据依然适用）· A5（回调句柄的 RAII）· 11 是底层原语、本体系是调度层｜**学**：04 第 14 课先补 11，再读本文件｜**记**：08 危险信号第⑥条 + 本节必背

---

## 0 · 这个体系解决什么问题

```cpp
// 经典事故现场（ROS2 初学者几乎必踩）
void MyNode::on_timer() {
    auto srv_client = ...;
    auto resp = srv_client->call_sync();   // ❌ 单线程 executor 里同步等服务 → 死锁
}
```

**模型一句话**：ROS2 的执行器把「事件（消息到达/定时器到点/服务请求）」变成「可调度的回调任务」，按线程模型与回调组规则去跑它们。**你的并发边界不是"线程函数"，而是"回调的并行度"。**

---

## 1 · 核心原则

### 1.1 回调模型 = 协作式事件循环（对比：线程模型）

| | 线程模型（你开线程） | 回调模型（executor 调度） |
| --- | --- | --- |
| 谁控制执行 | 操作系统 + 你 | 执行器（你控制线程数/回调组） |
| 块单元 | 线程函数 | **单个回调** |
| 最大风险 | 数据竞争（A2） | blocking-in-callback（饿死/死锁）+ 数据竞争 |

**推论**：调用的"并发度"由**回调组**决定，不由你写几行 `std::thread` 决定。

### 1.2 三种执行器（记住差异，选对场景）

```text
SingleThreadedExecutor          ：1 线程串行跑全部回调（确定性最好，最易调试）
MultiThreadedExecutor           ：N 线程并发跑；回调组约束并行
StaticSingleThreadedExecutor    ：半静态调度（降低运行时开销）——Jazzy 前默认推荐的"高性能"路径
```

### 1.3 回调组（官方语义，已核实）——并发度的唯一开关

```text
Mutually Exclusive（互斥）：组内回调绝不并发执行（默认；保证"组内数据不用锁"）
Reentrant（可重入）       ：组内回调可与自己并发（"可重入"=时序无关），也可与其它组并发
```

**用法与代价**：

```text
· 默认回调组是互斥 —— 想要并行必须显式建 Reentrant 组并分派（create_subscription(..., group)）
· 互斥组内=串行 ⟹ 可放心共享该组内数据（不用锁）——"用回调组结构替代锁"是 ROS2 的优雅之处
· Reentrant 组内=可并发 ⟹ 组内共享数据仍要自己加锁（回到 11）
```

### 1.4 黄金规则：回调必须是"短小的、非阻塞的、不分配的"

```text
❌ 阻塞：sleep / 同步等服务 / mutex 抢不到 / 大 I/O      → 饿死本线程所有其它回调（单线程=全部）
❌ 长任务：几秒的计算 / 重序列化                          → 同上
❌ 太贵的分配：字符串拼接 / vector 扩容 / 日志格式化       → jitter + 可能卡实时（18）
✅ 正确姿势：回调只做"搬运"——拷贝/入队/通知；重活交给工作线程（自己的线程池）或重新调度
```

**为什么这值得背（08 记忆卡）**：一个"看着没问题"的回调里藏一个 `sleep` 或 `call_sync`，就是"节点偶尔卡死"的全部原因。

### 1.5 回调的线程安全判据（接回 11）

- **互斥回调组内**：串行 ⟹ 组内数据无需锁（有保证）。
- **跨组 / 多 executor**：回调可能并行 ⟹ 共享数据要 mutex/atomic（照 11 决策）。
- 定时器回调和订阅回调跨组并行是常态——**共享成员变量一定加锁或只读**。

## 2 · 知识点地图（离散点）

| 点 | 一句话关键 | 注意 |
| --- | --- | --- |
| Executor::spin / spin_once / spin_some | 持续跑 / 跑一轮 / 跑到无就绪 | `spin_some` 别在回调里当"忙等"用 |
| add_node | 节点注册进执行器 | executor 对节点**持弱引用**（16，issue #726） |
| Timer | 周期性回调；`create_wall_timer(duration, cb)` | 时长类型 `std::chrono`；`rate.sleep()` 的语义 |
| 订阅回调 | 就绪即入队 | 高频+慢处理 → 队列积压（History QoS 决定缓冲） |
| 服务/动作回调 | 请求处理是回调；同步调用是陷阱 | 长服务处理也要出回调 |
| 回调组 | 互斥 vs 可重入（1.3） | 是 ROS2 的唯一"并发声明" |
| 工作线程模式 | 回调里入队，线程池执行重活，结果回发 | 最常用的解阻塞范式 |
| 锁优先级反转（延伸） | 低优先级持锁挡住高优先级 | 实时场景的深水区（18 提及） |
| `rclcpp::shutdown` | 全局退出；executor 停止 | 节点析构时机与回调的关系（16） |

## 3 · 决策流程：这个节点怎么组织并发

```text
Q1 我的回调有多重？
 ├─ 都轻（ms 级以下、不阻塞、不分配）→ 单线程 executor，默认组即可（最简单最确定）
 └─ 有的重 → Q2 重活能不能"搬运"（入队给工作线程）？
        ├─ 能 → 轻回调 + 工作线程（线程池）；executor 单线程即可
        └─ 不能 → Q3 需要真正并行吗？
                ├─ 是 → MultiThreadedExecutor + 按"不共享的数据"分 Reentrant 组
                └─ 否 → 分批/限流，仍单线程
Q4 有跨组共享数据吗？ → 有 → 按 11 加锁（别指望回调组救你）
```

**模板：读写分离的并发节点**：

```cpp
class Node : public rclcpp::Node {
  // 组1：接收回调（互斥，串行）→ 只写队列
  // 组2：处理回调（Reentrant 组 + 多线程 executor）→ 从队列取、算、发
  // 队列本身仍需 mutex（跨组共享）——用 11 的锁
};
```

## 4 · 常见坑（AI / 初学者代码高频）

| 坑 | 症状/原因 | 修法 |
| --- | --- | --- |
| 回调里 `sleep`/`rate.sleep` | 单线程 executor 全派停摆 | 定时用墙钟定时器；长处理出回调（1.4） |
| 回调里同步调服务 | 当场死锁（互相等） | 异步 client + 回调收结果 |
| 回调里 `spin()` | 递归执行 → 混乱/死锁 | 不要在回调里 spin（交给外层） |
| 默认互斥组却期望并行 | 重负载串行 | 显式 Reentrant 组 + 多线程 executor |
| 回调里字符串拼接/vector 扩容 | jitter + 实时性崩 | 预分配；格式化用轻量方式（18） |
| 把共享成员当"回调组保护了" | 跨组并行 race | 按 11 加锁 |
| 忘了 `add_node` 的节点 | 回调从不触发 | 检查 executor 持有节点（弱引用语义） |
| 回调里无条件 `use_count` 判断 | 竞态 | 用 lock/所有权模型（16） |

## 5 · 实践关联（动手清单）

```bash
# 环境无 ROS2 时：用纯 C++ 复刻"执行器模型"验证原则
# ① 复刻单线程执行器：一个线程串行跑回调 A/B/C，在 A 里 sleep → 观察 B/C 饿死
g++ -std=c++17 -pthread -x c++ - <<'EOF'
#include <thread>
#include <chrono>
#include <cstdio>
void run(const char* name, bool block){
    std::printf("%s 开始\n", name);
    if (block) std::this_thread::sleep_for(std::chrono::milliseconds(400));
    std::printf("%s 结束\n", name);
}
int main(){
    std::thread ex([&]{ run("A", true); run("B", false); run("C", false); });
    ex.join();
}
EOF
# → A 阻塞 400ms ⟹ B、C 全部被推迟（单线程执行器 = 协作式，天然饿死）

# ② 复刻"回调里同步等"死锁：单线程里 A 等 B、（B 永远等不到）
# ③ 用 TSan/ASan 检查：互斥组内共享数据 vs 跨组共享数据 谁触发了 race
```

## 6 · 与全局的连接

- **11**：本体系是 11 的"应用层"——回调内部的锁/atomic 全部照 11 决策；两者的边界是「回调组替你做了哪层同步」。
- **A2**：回调并发仍是 data race 判据；「互斥组内安全」是语言保证，不是约定。
- **A5**：定时器/订阅/回调句柄都是 RAII 对象——析构顺序决定悬垂（16）。
- **15** ROS2 层；**18** 实时下回调的分配纪律。

## 7 · 自测三问

- **判定**：单线程 executor 里，一个订阅回调里 `sleep(5s)`，另一个订阅回调会怎样？（饿死，延迟 5s+）
- **预测**：默认（互斥）回调组在 MultiThreadedExecutor 下能并行吗？（不能——组内串行；必须显式 Reentrant）
- **构造**：用纯 C++ 复刻一个"执行器 + 队列 + 回调"，验证：互斥组保证组内无 race；把某回调改成阻塞再观察饿死。
