# 24 · 工程化与工具链（专家交付的三标准）

> **专家的代码标准不是"能跑"**，而是三件事：**可维护 · 可验证 · 可复现**。
> 本文件把散在 `05`（实验命令）、`14`（排查）、`19`（构建插件）里的工具，收敿成一条**工程流水线**。
>
> **挂靠**：A1（符号/ODR）· 元原则 2（显式优于隐式）｜**记**：L3 查表为主；只需背「三套编译标志 + 五层关卡」

## 0 · 三标准与对应工具（先建骨架）

| 标准 | 含义 | 主要工具 |
| --- | --- | --- |
| **可维护** | 别人能改对、改便宜 | `clang-format` · `clang-tidy` · 模块边界（19）· API 设计（§7） |
| **可验证** | 有测试、有 sanitizer、有基准 | GTest/Catch2 · ASan/UBSan/TSan · benchmark · 覆盖率 |
| **可复现** | 同输入同输出，任何机器 | CMake 声明式依赖 · 锁定版本 · 无未初始化/无 UB · 确定性构建 |

## 1 · 编译标志：三套（开发 / 发布 / CI）

```bash
# ① 开发（快速迭代 + 抓错最狠）
g++ -std=c++20 -g -O1 -Wall -Wextra -Wpedantic -Wshadow -Wconversion \
    -fsanitize=address,undefined -fno-omit-frame-pointer

# ② 发布（性能）
g++ -std=c++20 -O2 -march=native -DNDEBUG -flto

# ③ CI（把警告当错误；跨编译器）
g++ -std=c++20 -Wall -Wextra -Werror -fsyntax-only ... && clang++ ... 同样跑一遍
```

**专家取舍**：

- `-Werror` 放进 CI，**不要**放进日常开发（会打断你；而且不同编译器警告不同，见 05 §11）。
- `-march=native` 只在**部署机等同构建机**时用；否则换 `-mtune`。
- **发布版要额外做一次 ASan 运行**（不是只在开发版做）——`-O2` 会暴露不同的 UB（见 14 §1）。

## 2 · 静态分析（不运行就能抓的 bug）

```bash
clang-tidy file.cpp -- -std=c++20 -Iinclude     # 需要 compile_commands.json（-DCMAKE_EXPORT_COMPILE_COMMANDS=1）
g++ -fanalyzer -fsyntax-only file.cpp           # GCC 自带路径敏感分析（慢但能抓资源泄漏/空指针）
cppcheck --enable=warning,performance file.cpp
include-what-you-use file.cpp                   # 减少头文件依赖（编译时间）
```

**checks 分类（记名字，细节现查）**：

```text
bugprone-*     真 bug（悬垂、用后释放、整数溢出）
performance-*  性能（不必要的拷贝、按值传参）
modernize-*    现代化（use-nullptr / use-override / use-auto / make_unique）
readability-*  可读性（命名、括号）
cppcoreguidelines-*  核心指南
```

**专家用法**：先用 `bugprone-*` + `performance-*`（收益最高），别一次开全套（噪声淹没信号）。

## 3 · 测试策略：四个层次

| 层 | 工具 | 测什么 | 具身智能对应 |
| --- | --- | --- | --- |
| 单元 | **GTest / Catch2 / doctest** | 函数/类的不变式 | 算法、数据结构 |
| 属性 | RapidCheck（属性测试） | 「对所有输入都成立」的性质 | 数值算法、解析器 |
| 模糊 | libFuzzer / AFL++ | 崩溃与 UB（配合 ASan） | 报文解析、传感器输入 |
| 系统/回归 | 仿真 + 基准 | 端到端行为、性能不退化 | SIL / HIL（21 §1 第 5 条） |

**专家规则**：**每个 bug 修完补一个测试**（否则它会回来）；**性能改动必须配基准**（否则"优化"是玄学，见 13 §3）。

```cpp
// Catch2 片段（单头文件，上手最快）
TEST_CASE("mean of empty is NaN") {
  REQUIRE(std::isnan(mean({})));          // 把"契约"写成可执行断言
}
```

## 4 · Sanitizer 矩阵（怎么组合，不能同时开哪些）

| 组合 | 抓 | 何时用 |
| --- | --- | --- |
| ASan + UBSan | 越界/悬垂/泄漏 + 溢出/空指针/对齐 | **每次测试都开** |
| TSan | 数据竞争 | 并发代码（**不能与 ASan 同开**） |
| MSan（clang） | 未初始化读 | 数值/协议代码（**不能与 ASan 同开**） |
| ASan + LSan | 泄漏 | 长跑集成测试 |

**专家判据**：**ASan/UBSan 常开；TSan 专门跑一遍并发测试；MSan 专门跑一遍数值测试。**

## 5 · 构建与依赖（可复现的关键）

```cmake
# 现代 CMake：以 target 为中心（不是目录为中心）
cmake_minimum_required(VERSION 3.20)
project(sim CXX)
set(CMAKE_CXX_STANDARD 20)
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)          # 给 clang-tidy 用
add_library(core src/core.cpp)
target_include_directories(core PUBLIC include)
target_compile_features(core PUBLIC cxx_std_20)
add_executable(app src/main.cpp)
target_link_libraries(app PRIVATE core)
```

| 依赖方式 | 何时用 |
| --- | --- |
| `find_package` | 系统已装的库 |
| `FetchContent` | 源码依赖，锁定 commit（可复现） |
| vcpkg / Conan | 多平台依赖管理（版本锁定 + 二进制缓存） |

**可复现三件事**：锁定依赖版本（commit/tag）· 固定工具链版本 · 构建产物带 hash（并记录编译命令）。

## 6 · ABI 与版本化（专家必懂，细节见 19）

```text
会破坏 ABI：加/删成员、改继承、改虚函数顺序、改模板签名、inline↔非inline、改 std 容器作为参数
不破坏 ABI：加非虚成员函数、改函数体、加新符号

版本化工具：
  inline namespace v2 { ... }   ← 同符号名不同版本共存（libstdc++ 就用它）
  -fvisibility=hidden + 导出宏   ← 只暴露接口（19 §1.2）
  soname 版本号                  ← 动态库的 ABI 身份
```

## 7 · API 设计（可维护的核心）

```text
专家清单（写完一个公共接口，过一遍）：
□ 所有权是否明确？（值/unique/shared/借用 —— 见 16 §1.1）
□ 参数用 string_view/span 还是 const&？（见 23 §10）
□ 单参构造是否 explicit？（元原则 2）
□ 错误怎么表达？（预期错误用 expected/error_code；异常错误才 throw —— 09 §1.3）
□ 是否 noexcept？（影响容器选择与优化 —— 09 §1.2）
□ 能否 const？（T1；不能 const 的地方要能解释为什么）
□ 头文件依赖是否最小？（前向声明/pImpl —— 19/22 §4）
```

## 8 · CI 流水线：五层关卡（对齐 03 第五节）

```text
第 0 层  格式化      clang-format --dry-run -Werror
第 1 层  编译告警    gcc + clang 两套，-Werror
第 2 层  静态分析    clang-tidy(bugprone,performance) + -fanalyzer
第 3 层  测试        单测 + ASan/UBSan；并发另跑 TSan；数值另跑 MSan
第 4 层  跨 TU/ODR   -flto -Wodr（08 的 ODR 检查）
第 5 层  基准回归    关键路径 benchmark，阈值报警（性能不许悄悄退化）
```

**这道流水线就是「工具优先于猜想」（14 §1）在团队尺度的展开**——让机器先说话。

## 9 · 实测清单（动手 15 分钟）

```bash
# ① 一条命令跑完第 1~4 层（存成 check.sh）
g++ -std=c++20 -Wall -Wextra -Werror -fsyntax-only f.cpp \
 && clang++ -std=c++20 -Wall -Wextra -Werror -fsyntax-only f.cpp \
 && clang-tidy f.cpp --checks='bugprone-*,performance-*' -- -std=c++20 \
 && g++ -std=c++20 -g -O1 -fsanitize=address,undefined f.cpp -o /tmp/f && /tmp/f

# ② ODR 关卡（跨 TU 类型不一致）
g++ -std=c++20 -O2 -flto -Wodr a.cpp b.cpp main.cpp -o prog

# ③ 可复现性自检：同一份源码两次构建，比较 .o 的符号表与关键段
nm -C a.o | sort > s1.txt && (重新构建) && nm -C a.o | sort | diff s1.txt -
```

## 10 · 自测三问

- **判定**：为什么 `-Werror` 该进 CI 而不该进日常开发？（不同编译器警告集不同 + 打断思路；CI 是"关卡"，本地是"助手"）
- **预测**：只在 `-O0` 跑测试、`-O2` 直接发布，会漏掉什么？（`-O2` 才会暴露的 UB —— 所以发布版也要跑一次 ASan）
- **构造**：为一个已有小项目补上「五层关卡」脚本，并故意引入一个 UB 和一个 ODR 违规，验证第 3/4 层能抓住。
