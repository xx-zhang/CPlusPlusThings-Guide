## 一、先做预测（不要往下翻）

**在看任何解释之前**，先凭直觉回答下面三个问题，写在纸上。这一步比后面读解释重要得多。

```cpp
// widget.h
#pragma once
struct Widget {
    static const int kMax = 100;    // (a)
    static int live_count;          // (b)
    int id;
};

template <class T>
T mymax(T a, T b) { return a < b ? b : a; }        // (c)

inline int clamp100(int x) { return x > 100 ? 100 : x; }   // (d)
int scale(int x) { return x * 2; }                          // (e)
```

这个头文件被 `a.cpp` 和 `b.cpp` **同时 include**，两个 `.cpp` 都使用了其中这些名字。然后一起链接成可执行文件。

**预测 1**：`(a)` ~ `(e)` 各自会发生什么？哪些能正常链接，哪些报错？

**预测 2**：`(a)` 有没有一个「平时没事、突然报错」的隐藏条件？

**预测 3**：`(b)` 和 `(e)` 各给出**两种**修法。

## 二、原则

> **编译器一次只看到一个 `.cpp` 预处理后的结果。它永远不知道别的翻译单元里有什么。**

这一条叫 **A1 翻译单元公理**。它的好处是**分离编译**（改一个文件只重编一个文件），代价是下面这一串必然结果：

1. **任何名字必须「全程序唯一，或被显式声明为可以有多份」** —— 这就是 **ODR**。
2. 编译器看不到别的 TU，**所以它无法替你合并重复定义** —— 合并是**链接器**的活。
3. 链接器靠什么区分「该合并」和「该报错」？—— **强符号 vs 弱符号**。
4. **`inline` 就是「把符号标成弱符号」的那把钥匙。**
5. 模板实例化需要看到**完整定义** —— 所以模板必须 header-only。

### 2.1 三把正交的尺子（这一课的核心工具）

| 轴 | 回答什么 | 取值 |
| --- | --- | --- |
| **作用域** scope | 这个名字**在源码哪里能写出来** | 块 / 函数 / 类 / 命名空间 |
| **链接性** linkage | 这个名字**别的 TU 能不能看见** | 外部 / 内部 / 无 |
| **存储期** storage duration | 这块内存**在哪、活多久** | automatic / static / thread / dynamic |

**三者完全独立。** 「头文件里能不能放定义」这个问题，**只由链接性决定**。

### 2.2 链接层面的机械真相

```text
强符号（T）  = 全程序只能有一份。出现两遍 → multiple definition
弱符号（W）  = 允许多份，链接器随便挑一份合并。→ 不报错
```

看符号的命令：

```bash
g++ -std=c++17 -c file.cpp -o file.o
nm -C file.o
```

| 字母 | 含义 | 大写 / 小写 |
| --- | --- | --- |
| `T` / `t` | 代码段符号 | 大写 = 外部链接，小写 = 内部链接 |
| `W` | **弱符号**（`inline` / 模板 / `constexpr` 函数 / 类内定义的成员函数） | — |
| `R` / `r` | 只读数据段 | 大写 = 外部（C 的 `const`），小写 = 内部（**C++ 的 `const`**） |
| `U` | 未定义引用（需要链接器去找） | — |

## 三、实测（跑起来，别只看）

### 实验 1 —— `inline` 到底做了什么

```bash
cd /tmp && mkdir -p l1 && cd l1

cat > h.h <<'EOF'
int add(int a, int b){ return a + b; }
EOF
cat > a.cpp <<'EOF'
#include "h.h"
int x(){ return add(1,2); }
EOF
cat > b.cpp <<'EOF'
#include "h.h"
int y(){ return add(3,4); }
EOF
cat > m.cpp <<'EOF'
int x(); int y(); int main(){ return x() + y(); }
EOF

g++ -std=c++17 a.cpp b.cpp m.cpp -o m
```

**预期看到**：

```text
/usr/bin/ld: b.cpp:(.text+0x0): multiple definition of `add(int, int)';
              a.cpp:(.text+0x0): first defined here
collect2: error: ld returned 1 exit status
```

现在**只改一个词**——`h.h` 第一行变成 `inline int add(...)`：

```bash
sed -i 's/^int add/inline int add/' h.h
g++ -std=c++17 a.cpp b.cpp m.cpp -o m && echo "✅ 链接通过"
```

### 实验 2 —— 看符号，理解为什么

```bash
g++ -std=c++17 -c a.cpp -o a.o
g++ -std=c++17 -c b.cpp -o b.o
nm -C a.o b.o
```

**预期看到**：

```text
a.o:                                 b.o:
0000000000000000 T x()               0000000000000000 T y()
0000000000000000 W add(int, int)     0000000000000000 W add(int, int)
                 ↑ 弱符号                             ↑ 完全相同的弱符号
```

**两个 `.o` 里有同名弱符号 ⟹ 链接器默默合并成一份。**

> **这就是 `inline` 的全部魔法。**它不是「建议编译器内联」，而是**给链接器的一条指令**。

### 实验 3 —— 证明 `inline` 与「内联」无关

```bash
cat > ni.cpp <<'EOF'
int __attribute__((noinline)) sq_noinline(int x){ return x*x; }
int sq_plain(int x){ return x*x; }   // 注意：没有写 inline
int f(int x){ return sq_plain(x); }
int g(int x){ return sq_noinline(x); }
EOF
g++ -std=c++17 -O2 -S ni.cpp -o - | grep -A 4 -E '^_Z1fi:|^_Z1gi:'
```

**预期看到**：

```text
_Z1fi:                        _Z1gi:
    imull %edi, %edi              jmp _Z11sq_noinlinei
    movl  %edi, %eax          ← 没内联
    ret                   ← 完全内联！但它没写 inline
```

**`sq_plain` 没写 `inline`，照样被完全内联。**
**`inline` 关键字和「内联」是两件独立的、由不同组件（链接器 vs 优化器）负责的事。**

### 实验 4 —— 三个真实的链接错误

```bash
# ① static 成员变量只声明、没定义
cat > s1.cpp <<'EOF'
struct W { static int cnt; };
int main(){ return W::cnt; }
EOF
g++ -std=c++17 s1.cpp -o s1        # → undefined reference to `W::cnt'
```

```bash
# ② static const int 类内初始化 + 取地址（ODR-use）
cat > s2.cpp <<'EOF'
struct A { static const int k = 7; };
int main(){ const int* p = &A::k; return *p; }
EOF
g++ -std=c++11 s2.cpp -o s2        # → undefined reference to `A::k'
```

**这个最阴**：`A::k` 在类内初始化了、`A::k` 用起来也没问题，**一旦取地址就突然链接报错**。
因为类内初始化给的是**值**，不是**定义**。

```bash
# ③ C 与 C++ 的 const 链接性差异
echo 'const int c = 42;' > x.c
gcc -c x.c -o x_c.o          && echo "C  : $(nm x_c.o | grep ' c$')"
g++ -c x.c -o x_pp.o -x c++  && echo "C++: $(nm x_pp.o | grep ' c$')"
```

**预期看到**：

```text
C  : R c      ← 大写 = 外部链接
C++: r c      ← 小写 = 内部链接
```

**C 的 `const int c` 是外部链接**（两个 TU 都写会 `multiple definition`）；
**C++ 的是内部链接**（每个 TU 各一份，互不冲突）。
这是仓库 `const/README.md` 最大的错误来源——**把 C 的知识搬到了 C++ 里**（详见 `06-仓库审计报告.md` §1.1）。

### 实验 5 —— 完整答案表

| | 是什么 | 符号 | 头文件能放吗 | 依据 |
| --- | --- | --- | --- | --- |
| **(a)** `static const int kMax = 100;` | 类内**初始化**（给值），**不是定义** | 不产生符号（未 odr-use 时） | ✅ | 一旦取地址 / 绑引用，需要类外定义 |
| **(b)** `static int live_count;` | 类内**只是声明** | `U`（未定义引用） | ✅ 声明可以，**定义必须在恰好一个 `.cpp`** | A1 |
| **(c)** `template <class T> T mymax(...)` | 模板函数定义 | `W` 弱符号（隐式 inline） | ✅ | 模板实例隐式 inline |
| **(d)** `inline int clamp100(int)` | 显式 inline | `W` 弱符号 | ✅ | 显式 inline |
| **(e)** `int scale(int)` | 普通函数定义 | `T` 强符号 | ❌ | A1：强符号只能有一份 |

**`(a)` 的隐藏条件（预测 2 的答案）**：

```cpp
Widget w;
const int& r = Widget::kMax;        // ← odr-use：绑引用
const int* p = &Widget::kMax;       // ← odr-use：取地址
std::max(Widget::kMax, w.id);       // ← 可能 odr-use（按 const int& 传参）
```

**只要发生 odr-use，就需要定义**。所以「平时没事、突然报错」是真的。

**`(b)` 的两种修法**：

```cpp
// 修法 1（传统）：在恰好一个 .cpp 里定义
// widget.cpp
int Widget::live_count = 0;

// 修法 2（C++17）：
struct Widget { static inline int live_count = 0; };
```

**`(e)` 的两种修法**：

```cpp
// 修法 1：加 inline，保持在头文件
inline int scale(int x) { return x * 2; }

// 修法 2：头文件只留声明，定义移到 .cpp
// widget.h
int scale(int x);
// widget.cpp
int scale(int x) { return x * 2; }
```

> ⚠️ **注意修法 1 和修法 2 的语义差别**：
> `inline` 是「多份定义**合并成同一份**」（地址相同）；
> 如果改成 `static int scale(...)`，则是「每个 TU **各留一份独立副本**」（地址不同，可能代码膨胀）。
> **这两个选择在运行时行为上是不同的**（比如函数局部 static 变量会被复制多份）。

## 四、这一课在 AI 生成的代码里对应的坑

AI 写 C++ 时，这三类错误出现的频率极高：

### 坑 1 · `multiple definition of 'X'`

**长什么样**：头文件里有**函数体**或**变量定义**（不是声明）。

```cpp
// util.h  ❌
int global_counter = 0;                    // 变量定义
int helper(int x) { return x * 2; }        // 函数定义
```

**为什么 AI 会犯**：它在「写一个自包含的小例子」的心智模式下，会把定义和声明混在一起。单文件编译时完全没问题，一拆多文件就炸。

**修法**：加 `inline`、改成 `static`、移进 `.cpp`、或（变量）改成 C++17 的 `inline` 变量。

### 坑 2 · `undefined reference to 'X'`

**长什么样**：三种最常见

```cpp
// ① 模板定义放进了 .cpp  ❌
// matrix.h
template <class T> class Matrix { T get(int i) const; };   // 只声明
// matrix.cpp
template <class T> T Matrix<T>::get(int i) const { ... }    // 定义在 .cpp
```

**为什么错**：模板实例化需要**看到定义**。别的 TU 只看到声明，编译器无法实例化 → 链接器找不到符号。
**这就是「模板必须 header-only」的完整理由**（A1 的直接推论）。

```cpp
// ② static 成员变量忘了类外定义 ❌
struct Sim { static int step_count; };      // 只有声明
// 缺了 int Sim::step_count = 0;
```

```cpp
// ③ static const int 取了地址（见实验 4 ②）❌
```

**修法**：模板移到头文件（或显式实例化）；`static` 成员补一行类外定义（或 C++17 `static inline`）。

### 坑 3 · 跨 TU 的 `struct` 定义不一致（**静默、不报错、最难查**）

```cpp
// a.cpp
struct Config { int n; };
// b.cpp
struct Config { double n; };   // ← 改了却忘了同步！各自编译都不报错
```

**不报错，链接通过，运行时读到错的内存布局。**

**检测方法**：

```bash
g++ -std=c++17 -O2 -flto -Wodr a.cpp b.cpp main.cpp -o prog
```

实测输出：

```text
a.cpp:1:8: warning: type 'struct Config' violates the C++ One Definition Rule [-Wodr]
b.cpp:1:8: note: a different type is defined in another translation unit
a.cpp:1:16: note: the first difference of corresponding definitions is field 'n'
```

**这条对 CAE/EDA 特别重要**：这类项目里配置结构体、网格数据结构经常跨几十个 TU 共享，一个字段改动没同步就是灾难。

## 五、自测题（先自己答，再翻答案）

**题目**：下面这个头文件被 `a.cpp`、`b.cpp`、`c.cpp` **三个** TU 同时包含并链接。

```cpp
// sim.h
#pragma once
#include <vector>
#include <string>

const int kMaxIters = 1000;        // (1)
constexpr int kDof = 3;            // (2)
std::string g_name;                // (3)
static int g_count = 0;            // (4)
inline int twice(int x){ return 2*x; }        // (5)
int square(int x){ return x*x; }              // (6)
template <class T> T cube(T x){ return x*x*x; }   // (7)
```

**问题**：

**Q1**：`(1)` ~ `(7)` 各自会发生什么？（能链接 / `multiple definition` / `undefined reference` / 其他）

**Q2**：`(4)` 有一个区别于 `(5)` 的**语义差异**，是什么？（提示：看地址）

**Q3**：如果 `c.cpp` 里出现 `&kMaxIters`（取 `(1)` 的地址），会怎样？为什么？

**Q4**：`(6)` 的两种修法，以及这两种修法在**「函数内有 `static` 局部变量」**时的行为差异。

---

## 六、答案

### Q1

| | 声明 | 符号 | 结果 |
| --- | --- | --- | --- |
| **(1)** `const int kMaxIters = 1000;` | 命名空间作用域 `const` | `r`（内部链接） | ✅ 能链接。**每个 TU 各一份**——不报错，因为内部链接 |
| **(2)** `constexpr int kDof = 3;` | C++11：`constexpr` ⟹ 隐式 `const` ⟹ **内部链接** | `r`（内部链接） | ✅ 能链接，同上。**注意：C++17 起 `constexpr` 命名空间作用域变量仍是内部链接，除非写 `inline constexpr`** |
| **(3)** `std::string g_name;` | 普通全局变量**定义** | `B`（外部链接，BSS） | ❌ **`multiple definition of 'g_name'`** |
| **(4)** `static int g_count = 0;` | **内部链接**的全局变量 | `b`（小写 = 局部符号） | ✅ 能链接，但**每个 TU 各一份独立副本** |
| **(5)** `inline int twice(int)` | 显式 inline | `W` 弱符号 | ✅ 能链接，**合并成同一份** |
| **(6)** `int square(int)` | 普通函数定义 | `T` 强符号 | ❌ **`multiple definition of 'square(int)'`** |
| **(7)** `template <class T> T cube(T)` | 模板定义 | `W` 弱符号（隐式 inline） | ✅ 能链接 |

### Q2

`(4)` `static` 与 `(5)` `inline` 的**语义差异**：

> **`inline` 是「三份定义合并成同一份」（同一个地址）；
> `static` 是「三个 TU 各留一份互相独立的副本」（三个不同地址）。**

验证方法：

```cpp
// sim.h
static int& getCountStatic(){ static int n = 0; return n; }   // 或直接用 &g_count
inline int& getCountInline(){ static int n = 0; return n; }
```

在 `a.cpp` 和 `b.cpp` 里分别打印这两个地址：

```text
&g_count（static）  : a=0x...100  b=0x...200   ← 不同地址！两份
&...inline...（inline）: a=0x...300  b=0x...300   ← 相同地址！一份
```

**实际影响**：

- 用 `static` 放「全局计数器」会得到**三个独立的计数器**，各自计各自的——这是经典的静默 bug。
- `inline` 里如果有函数局部 `static` 变量，那**一个**变量被所有 TU 共享。
- **`static` 会让每个 TU 的代码里都有一份函数体（代码膨胀）；`inline` 不会。**

### Q3

```cpp
// c.cpp
const int* p = &kMaxIters;
```

**答**：**没问题，仍然能链接。**

因为 `(1)` 是**内部链接**的**变量定义**（不是类内初始化）。它**本来就有定义**——就在 `c.cpp` 里（通过头文件复制进来的那一份）。
所以取地址拿到的是 `c.cpp` 里那一份的地址。

> **对比第 4 节实验 4 ②**：`struct A { static const int k = 7; };` 之所以取地址会报 `undefined reference`，是因为**类内初始化给的是「值」而不是「定义」**——它根本没为 `k` 分配存储。
> 而 `(1)` 是**命名空间作用域的变量定义**，有存储。
>
> **两者的区别是「类内静态成员」vs「命名空间作用域变量」**，不是「const 不 const」。

### Q4

`(6) int square(int x){ return x*x; }` 的两种修法：

```cpp
// 修法 1：加 inline（保留在头文件）
inline int square(int x){ return x * x; }

// 修法 2：声明留头文件，定义移到恰好一个 .cpp
// sim.h
int square(int x);
// sim.cpp
int square(int x){ return x * x; }
```

**当函数内部有 `static` 局部变量时，两者行为不同**：

```cpp
inline int counter(){ static int n = 0; return ++n; }
// 修法 1（inline）：所有 TU 共享同一个 n  → 总共数到 N
```

```cpp
int counter();   // 头文件只声明
// sim.cpp
int counter(){ static int n = 0; return ++n; }
// 修法 2：只有 sim.cpp 有这个 n        → 总共数到 N（同样共享，因为只有一个定义）
```

```cpp
static int counter(){ static int n = 0; return ++n; }   // ⚠️ 第三种：static
// 每个 TU 有自己的 n 和自己的 counter → 每个 TU 各自从 1 开始数！
```

**结论**：

- **修法 1（`inline`）和修法 2（移到 `.cpp`）在语义上等价**——都只有一份函数、一份 `static` 局部变量。差异只是**编译期依赖**（`inline` 让改动会触发所有 TU 重编）。
- **`static` 函数才有语义差异**（多份独立副本）。**这是选 `static` 前必须想清楚的。**
