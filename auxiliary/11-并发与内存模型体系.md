## 0 · 这个体系解决什么问题

CAE/EDA 计算几乎必然并行。而 AI 生成的并发代码最常见的四个问题：

```cpp
volatile bool stop = false;        // ❌ 用 volatile 做线程同步（08 已实测丢计数）
while(!stop) { work(); }           // data race = UB，不是"可能读到旧值"
// 线程2： stop = true;
```

本体系给你三件确定的事：**① 正确性判据（happens-before）；② 同步工具怎么选；③ 出问题时怎么定位（TSan）。**

---

## 1 · 核心原则

### 1.1 data race 是 UB，不是「结果不确定」（A2）

C++11 内存模型的底线：**两个线程无同步地访问同一内存、至少一个写** ⟹ **data race** ⟹ **UB**（整个程序无定义）。

要点：

- **「跑对了」不证明没有 race**。本机实测（08 已录）：裸 `int++` 三局全对——因为 x86 上对齐的单条 `addl` 指令天然原子。**换个编译器/布局就可能丢**；同机的 `volatile int` 版三次丢成 212561/329722/226264。
- **别等崩溃/错值**：race 经常静默。用 **TSan** 主动抓（本机用法见 08：`setarch $(uname -m) -R` 修复 ASLR 冲突）。

### 1.2 正确性 = 建立 happens-before 关系

> **两个线程要「有序地看到」同一份数据，必须通过同步原语建立 happens-before（偏序）边。**

- `mutex` 的 `lock/unlock`：解锁 happens-before 下一次加锁——**临界区里写的数据，别人加锁后读，必可见**。
- `atomic` + `acquire/release`：`store(release)` happens-before `load(acquire)`——生产者发布，消费者获取。
- 没有这条边 = 没有保证（哪怕原子化读写了，顺序仍可能乱）。

**所以判断并发代码正确与否，问一句：两个线程对每个共享变量之间，有没有一条 happens-before 链？没有 = 一定有 race 风险。**

### 1.3 volatile ≠ 同步（最贵的错误认知）

| `volatile` 保证 | 不保证 |
| --- | --- |
| 编译器不合并/删除这次访问 | **原子性**（读-改-写不是原子的） |
| 每次真的访存 | **内存序**（CPU/编译器可重排） |
| 用于 MMIO、setjmp、sig_atomic_t | **跨线程可见性**（内存模型不管它） |

**替代**：`std::atomic<bool>`（+ 明确 memory_order）。

### 1.4 共享你的程序里真正需要什么：先问三问再写锁

```text
Q1 这些线程真的共享这块内存吗？（还是各自算各自的，最后合并）
Q2 谁写？谁读？读写频率？
Q3 是一次性发布（一写多读）还是持续竞争？
```

- 一写多读、一次性 → `atomic` release/acquire 就够了
- 持续竞争小临界区 → `std::mutex` + `lock_guard`
- 大批数据计算 → 尽量**无共享**（各线程自己的 slot），合并时一次性同步（这往往比加锁快一个数量级）

## 2 · 知识点地图（离散点）

| 点 | 一句话关键 | 注意 |
| --- | --- | --- |
| `std::thread` | 创建即运行；**必须 join 或 detach**，析构时未决定 = `std::terminate` | `jthread`（C++20）析构自动 join |
| `mutex` / `lock_guard` / `unique_lock` / `scoped_lock` | RAII 加锁（A5）；`scoped_lock`（C++17）可同时多锁防死锁 | **别裸 lock/unlock** |
| 死锁 | 两个线程按相反锁序拿两把锁 | 全项目**统一锁序**；或 `std::scoped_lock` 一次拿齐 |
| `condition_variable` | `wait` 必须**放在 `while` 循环**里（虚假唤醒 + 条件重查） | `wait(lock, pred)` 等价封装；`notify_one`/`notify_all` |
| `atomic<T>` | 无锁原子操作；`fetch_add`/`exchange`/`compare_exchange` | 但 CAS 循环可能忙等 |
| memory_order 阶梯 | `relaxed < consume < acquire/release < acq_rel < seq_cst`（默认 seq_cst 最安全最贵） | 初学只用默认 + acquire/release |
| `thread_local` | 每线程一份存储（A3 存储期的 thread 值） | 与 global 不同，无跨线程 race |
| `async`/`future`/`promise` | 高层任务模型；`future.get()` 阻塞 | 注意任务在 future 析构时同步 |
| 单例线程安全 | 函数内 `static` 局部量：**C++11 起线程安全惰性初始化**（实测：两个线程同时 `get()` 只构造一次） | Meyers 单例 = 一行 |
| TSan | 数据竞争检测器 | 本机 `setarch -R` 修 ASLR；**与 ASan 分开关** |

## 3 · 决策流程：这段并发代码怎么同步

```text
两个线程要碰同一块内存
 │ Q1 是 data race 吗？（无同步 + 至少一写）
 ├─ 是 → 必改，否则是 UB（TSan 验证）
 │
 └─ 需要同步 → Q2 关系是"发布-消费"吗？（一写多读、一次性）
        ├─ 是 → atomic + acquire/release（最轻）
        └─ 否 → Q3 是竞争式修改吗（读-改-写）
                ├─ 是 → atomic::fetch_add / compare_exchange
                │       或 mutex（临界区大时）
                └─ 否 → mutex 保护临界区（lock_guard/scoped_lock）
                        + Q4 需要等待条件吗？
                          ├─ 是 → condition_variable（wait(lock,pred)）
                          └─ 否 → 完成
```

**线程安全类的写法模板**：成员 = 数据 + 一把 `mutable std::mutex m_;`，每个公开方法 `std::lock_guard lk(m_);` 开头。**注意：不要把锁当"返回值"的传递凭据；别在持锁时调用外部回调（可能反向加锁/死锁）。**

## 4 · 常见坑（AI 代码高频）

| 坑 | 症状/原因 | 修法 |
| --- | --- | --- |
| `volatile` 做同步 | 结果偶尔错（08 实测丢计数） | `std::atomic<bool>` |
| 忘 join/detach | 析构 thread → terminate | `jthread` 或显式 join；detach 前想清楚生命周期 |
| 死锁（锁序相反） | 两个线程互相等 | 全局统一锁序；`scoped_lock` 一次拿多把 |
| 持锁调用外部回调 | 回调反向加锁 → 死锁 | 拷贝所需数据，出临界区再回调 |
| `cv` wait 没用 while | 虚假唤醒漏判 | `cv.wait(lock, []{...})` 带谓词 |
| 忘 notify_one | 等待者永久阻塞 | 状态变化后一定 notify；`notify_all` 保守可用 |
| 裸 int 计数 | 看似对实则 UB（x86 假象） | `atomic`，TSan 验证 |
| `future` 忘 get | 异常被吞（future 析构丢弃异常） | 捕获异常显式处理 |
| data race 但"没崩" | 静默损坏 | TSan（见 08 修法） |

## 5 · 实践关联（动手清单）

```bash

# ② TSan 抓 race（本机要关 ASLR）
g++ -std=c++17 -g -O1 -fsanitize=thread /tmp/v2/race3.cpp -o race3

# ③ 验证 Meyers 单例线程安全
```

## 6 · 与全局的连接

- **A2**：data race = UB 是并发版公理；「跑对了」在 x86 有陷阱（08 反例）。
- **A5**：所有锁都用 RAII（`lock_guard`/`scoped_lock`）——异常安全与解锁同时保证。
- **A3**：`thread_local` = 存储期的第 4 个取值（automatic/static/thread/dynamic）。
- **08**：§1.7 第⑥条 + volatile/TSan 反例两行；**07** 图谱⑪。

## 7 · 自测三问

- **判定**：`volatile bool stop` 两个线程一读一写，是 data race 吗？（是——UB；volatile 不改变这一点）
- **预测**：一个 `std::atomic<int>` 用默认 seq_cst 做计数器，会比 `mutex` 快多少？什么时候反而慢？（竞争激烈时 CAS 忙等可能更差——实测）
- **构造**：写一个生产者-消费者，用 `condition_variable` + while 谓词，先用 TSan 证明无 race，再故意删掉 `notify` 观察永久阻塞。
