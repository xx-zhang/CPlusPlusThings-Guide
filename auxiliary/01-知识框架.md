## 第 0 层 · 为什么需要一个框架

仓库里 95 篇「那些事」的组织方式是「主题 → 结论 → 代码」。这种组织方式有一个致命的认知缺陷：

**它把「同一个原因的不同表现」当成了「不同的知识点」。**

举三个例子：

| 仓库里看起来无关的三个知识点 | 实际上是同一件事 |
| --- | --- |
| `static` 成员变量忘了类外定义 → 链接错误 | 都是 **A1 翻译单元公理** |
| `inline` 函数可以放头文件，普通函数不可以 | 都是 **A1 翻译单元公理** |
| 模板必须 header-only，不能放 `.cpp` | 都是 **A1 翻译单元公理** |

| 仓库里看起来无关的三个知识点 | 实际上是同一件事 |
| --- | --- |
| `sizeof(空类) == 1` | 都是 **A3 对象模型公理** |
| 多态对象里有一个 vptr，多继承有多个 | 都是 **A3 对象模型公理** |
| RAII 为什么能保证释放资源 | 都是 **A3 对象模型公理**（生命周期是对象的独立属性） |

| 仓库里看起来无关的四个知识点 | 实际上是同一件事 |
| --- | --- |
| `-O2` 下 `if (x + 1 > x)` 被优化成恒真 | 都是 **A2 抽象机公理** |
| 数组越界"看起来还能跑" | 都是 **A2 抽象机公理** |
| 数据竞争不是"结果不确定"而是"程序无意义" | 都是 **A2 抽象机公理** |
| `reinterpret_cast` 之后访问数据偶尔出错 | 都是 **A2 抽象机公理** |

**知识的压缩比就在这里**：95 张卡片 ⟶ 5 条模型 + 12 条定理。

而这个压缩比带来一个实际能力：**当你遇到一张卡片上没写过的变体时，你可以从公理推出来，而不是去猜。**

## 第 0.5 层 · 元公理：这套框架建立在什么之上

> 这一层回答三个更深的问题：**① 五条公理（A1-A5）从哪来？② 凭什么说它们自洽？③ 完整的边界在哪？**

> **这一层不属于 C++** —— 它是可以迁移到任何复杂系统上的思维模式，C++ 只是它的第一个用例。
> 加压自检、已知张力、生活/工作延申见 **`00-方法论自检与迁移.md`**。

### 0.5.1 · 五条公理不是「选」出来的，是「投影」出来的

A1-A5 不是拍脑袋挑的规则，而是四条**底层设计决策**在语言结构上的投影。
设计决策才是真正的「元公理」：它们是不可再化简的动机，其余一切规则都是它们的必然结果。

| # | 底层设计决策 | 含义 | 投影成 |
| --- | --- | --- | --- |
| **D1** | 分离编译 | 改一个文件只重编一个文件 ⟹ **编译器一次只见一个 TU** | **A1** 翻译单元公理 |
| **D2** | 值语义 + 显式生命周期 | 对象是你拥有的存储上的结构，不是 GC 下的引用；生与死由你决定 | **A3** 对象模型公理 |
| **D3** | 性能优先，允许激进优化 | 优化器在「抽象机 + as-if」内可任意重排、删除、假定 | **A2** 抽象机公理 |
| **D4** | 能编译期定的事，不留到运行期 | 静态类型、重载、模板、constexpr 优先 | **A4** 分层公理 |
| **D5** | 与 C 兼容 + 历史延续 | 语法与语义的继承与妥协 | 「**约定域**」（见 0.5.4） |

> **出处**：这套表不是我的发明，而是把 Bjarne Stroustrup《The C++ Programming Language》自己陈述的设计目标**公理化**了——**零开销抽象**（→D2/D3/D4）、**直接映射硬件与内存**（→D2/D3）、**与 C 兼容**（→D5）、**分离编译**（→D1）。框架的职责只是把他的话变成可推演的结构。

### 0.5.2 · 逻辑自洽：依赖图无环 + 多路径互证（不是循环论证）

「公理互相解释」的正确含义**不是**「A1 推出 A2、A2 推出 A1」（那是循环论证），而是两条可验证的性质：

**性质 ①：依赖图无环——有些「公理」其实是定理**：

```text
D1 ──→ A1（真模型：横切，关于名字与文件）
D2 ──→ A3（真模型：本体论，世界有什么）
D3 ──→ A2 ──┐
D4 ──→ A4 ──┘   ← A2 与 A4 同源：都是「零开销抽象」的两面
A3 ──→ A2 的定义域    ← A2 的状态 = A3 的对象（世界-语义，非并列！）
A3 + 栈展开保证 ──→ A5   ← A5 是定理级：RAII = 「生命周期独立」+「析构必被调用」
```

> **结构比"五条"更诚实的写法**：不是五条平铺——是「2 组 2 个 + 1 条推论」：运行期一对（A3 世界 + A2 语义引擎），编译期一对（A1 翻译 + A4 何时决定），A5 挂在其上的推论。

- **A5 的位置最弱**：它不是独立假设，是两步推出的结论。把它当公理是「教学上的方便」，不是「逻辑上的必需」。
- **A1 是横切的**：它关于「名字与文件」，与其余关于「对象与执行」的公理正交——这正是 `static` 的三个含义能落到「三把尺子」上的原因。

**性质 ②：多路径互证——从不同公理出发，到达同一现象时结论一致**：

| 现象 | 路径一 | 路径二 | 结论一致？ |
| --- | --- | --- | --- |
| const 与 `#define` 的「拷贝」之争 | A1（const 是内部链接变量） | A4（const 不是编译期常量） | ✅ 同一结论 |
| 构造函数里调虚函数不派发 | A4（运行期才知动态类型） | A3（vptr 构造期才写入） | ✅ |
| 声明虚析构 ⟹ 失去移动能力 | T4（特殊成员生成规则） | A5（析构 = 资源接口面） | ✅ |
| `final` 能去虚化 | A4（编译期可证明动态类型） | T5（分派三层的判据） | ✅ |

> 所以「逻辑自洽」的正面证据是：**系统内不存在互相矛盾的推论**。反面证据同样可查——任何一条定理被实测推翻，都会沿依赖图向上定位到某条公理/决策，而不是孤立打补丁。

### 0.5.3 · 认识论：这是「实证的、开放的」模型，不是教条

> **名相校正**：五条更适合叫**「五个模型/支柱」**（A1 翻译模型 · A3 对象模型 · A2 抽象机模型 · A4 分层模型 · A5 资源模型）——「公理」是教学压缩，不是形式化承诺。且它们**不是地位相同的五条**：A2 的定义域是 A3（世界-语义），A1/A4 管"程序从哪来、何时定"，A5 是推论（详见 0.5.2 依赖图）。称"公理"出了问题就修标签，不修内容。

| | 数学公理 | 本框架的公理 |
| --- | --- | --- |
| 地位 | 纯约定（不可被经验证伪） | 描述**自然规律层面**的事实（**可被编译器/标准证伪**） |
| 检验 | 一致性 + 独立性 | 一致性 + 独立性 + **实测** |
| 演进 | 可替换（如平行公理） | 可修订（新特性需新公理） |

**三条「好公理集」的判据（跨领域通用）**：

1. **独立**：没有一条能由其余几条推出（A5 不满足，故降格为定理）。
2. **生成力 / 覆盖**：能推出解释域内绝大多数规则。
3. **可证伪 / 可修订**：每条都能被实测检验；新事实来了能扩，而不是硬坳。

### 0.5.4 · 边界：能解释什么、不能解释什么——「四域分类」

「能解释所有 C++ 内功」的**正确读法**不是「一切皆可证」，而是：**可推演的推演；约定的标定；实现定义的给方法；其它系统的承认**。

| 域 | 是什么 | 例子 | 框架怎么对待 |
| --- | --- | --- | --- |
| **① 可推演域（定理）** | 语言机制的必然结果 | 对象/生命周期/RAII/链接/值类别/多态/UB/异常安全/模板 | 从公理**推**出来（框架的真正价值：能预判变体） |
| **② 约定域（定义/历史）** | 推不出来的「定义」与历史遗留 | `static` 三义、`++i` 惯例、`operator<<` 输出、`vector<bool>` 位压缩、`class`/`typename` 双拼写 | **标定为约定**，背下来即可；别误以为是定理 |
| **③ 实现定义域** | ABI 决定的具体数字 | `sizeof`、偏移、虚表布局、`int` 大小 | 给**推导规则 + 实测命令**（05 工具箱），不背书数字 |
| **④ 其它系统** | 另一套知识系统 | 容器/算法复杂度选择、设计模式、数值方法、构建系统、C++20 模块 | **承诺分类，不承诺解释** |

> **数学类比**：公理化系统里有两类陈述——**定理**（可证）与**定义**（约定）。「导数」的定义是选择，不是定理；实数公理推不出「拓扑空间」。**框架的价值同样在于划界线：让每一张知识卡片都知道自己是哪一类。**
>
> **落地建议**：给仓库 95 篇「那些事」打四个标签——`理论` / `约定` / `实现定义` / `领域`。你的「三行笔记」（03 的第六步）里那行「前提」，本质就是这个分类动作。

**三个内在局限（承认它们，模型才可信）**：

1. **C++ 语义本身没有形式完备性**：标准有已知缺陷、未指定行为、编译器实现差异。完备性承诺在此语境下不存在。
2. **新特性需要新公理**：协程、模块、反射会修订 A1/A5 的实现方式——公理系统是**开放可修订**的，这使它像科学理论而非教条。
3. **解释力 ≠ 预测力**：语言规则管「**必然**」；优化器、库、编译器的工程决策管「**实然**」——实然仍需实测兜底。**公理负责必然，实测负责实然**（回到 03 的六步法）。

### 0.5.5 · 可迁移的思维模式（这一层真正的价值）

**通用元方法（五步）**——适用于任何复杂系统：

```text
① 找设计决策   问「它为什么要这样做」→ 找到不可再化简的动机（D 层）
② 投影成公理   问「哪些规则是必然结果」→ 形成最小结构公理集（A 层）
③ 推演与标定   问「这是定理还是定义」→ 推得出的推，推不出的标为约定
④ 实测闭环     问「我怎样才能证伪它」→ 用经验/实验验证每一条
⑤ 划边界       问「哪些是另一套系统的事」→ 诚实声明覆盖范围
```

**适配场景**（同一个五步）：

| 系统 | D 层（设计决策）→ A 层（结构公理）→ 约定域 |
| --- | --- |
| **操作系统** | 虚拟内存、进程隔离 → 地址空间是公理 → fork/页表开销全是推论；系统调用 API 命名是约定 |
| **Rust** | 单一所有权（D2 的激进版）→ 借用检查器的一切规则都从「一个值一个主人」推出 → `unsafe` 是约定域 |
| **数据库** | ACID 事务 → 「原子性 + 隔离性 ⟹ 一致性」是推导；索引策略是领域知识 |
| **代码审查** | 先把一段代码分类（机制/约定/实现细节）→ 再决定要不要花力气推演 → 不把「约定」当「定理」审 |
| **任何「背了很多规则」的领域** | 你背的东西里至少 40% 是「某条公理的推论」，背它不如推它；剩下的是约定，背它不如标定它 |

> **记忆口诀**：**「必要的是定理，不必要的是约定；能证伪的是科学，不能证伪的是信仰。」**
> 这套模型的终极用途，是把记忆负担从「背 95 条」降到「记 5 条 + 会分类」。

### A1 · 翻译单元公理

> ### **编译器一次只看到一个 `.cpp` 预处理后的结果。它永远不知道别的翻译单元里有什么。**

#### 为什么这是公理

这是 C++（以及 C）**分离编译（separate compilation）** 模型的根本设定。它换来的好处是：改一个 `.cpp` 只需重编一个 `.cpp`（而不是全程序重编）——这是 C++ 能编译百万行级项目的唯一原因。代价就是下面这些规则。

#### 直接推论（全部是必然结果，不是「约定」）

1. **任何名字必须「要么全程序唯一，要么被显式声明为可以有多份」。** 这就是 **ODR（One Definition Rule）**。
2. 名字的「全局可见性」是一个独立属性 ⟹ 这就是 **链接性（linkage）**。
3. 因为编译器看不到别的 TU，所以**它无法替你合并重复定义** ⟹ 合并是**链接器**的活 ⟹ 所以必须有「弱符号」机制 ⟹ 这就是 **`inline`**。
4. 模板实例化需要看到**完整定义** ⟹ 模板必须 header-only 或显式实例化。
5. `static` 的三种含义，恰好各占一个正交轴（见 `02` 的第一张表）。

#### 链接层面的机械真相（实测）

`inline` 到底做了什么？答案是：**它让编译器把符号标成「弱符号（weak）」而不是「强符号（strong）」**。

```text
$ nm -C a.o b.o
a.o:
0000000000000000 T x()                          ← T = 强符号（普通函数）
0000000000000000 W ce(int)                      ← W = 弱符号（constexpr 函数）
0000000000000000 W int mymax<int>(int, int)     ← W = 弱符号（模板实例）
0000000000000000 W S::f()                       ← W = 弱符号（类内定义的成员函数）

b.o:
0000000000000000 W ce(int)                      ← 同样的三个弱符号
0000000000000000 W int mymax<int>(int, int)
0000000000000000 W S::f()
```

**两个 `.o` 里有完全相同的三个弱符号 ⟹ 链接器默默合并成一份，不报错。**
**对照：普通函数是强符号 `T`，出现两份就 `multiple definition`。**

> **`inline` 的主职是「告诉链接器：这个符号允许多份，随便挑一份」。**
> 至于内不内联，**完全由优化器自己决定**——实测：没写 `inline` 的函数在 `-O2` 下照样被内联。

#### 仓库章节映射

`basic_content/extern` · `basic_content/static` · `basic_content/inline` · `basic_content/const`（第 3 节）· `basic_content/using` · 一切模板章节

#### 常见误解（仓库里就有的）

| 误解 | 真相 |
| --- | --- |
| 「`inline` 是建议编译器内联」 | `inline` 是**给链接器的指令**（放宽 ODR）。内联与否是优化器的事 |
| 「`const` 变量只有一份拷贝」 | 命名空间作用域 `const` 是**内部链接**，**每个 TU 各一份**。实测两个 TU 各写 `const int c`（值 1 和 2），链接通过、各用各的 |
| 「`static` 成员变量在类内声明并初始化即可」 | 类内给的是**值**（对 `static const`/`constexpr`）或**只是声明**（对普通 `static`）。**谁定义？必须恰好一个 `.cpp`** |
| 「C 和 C++ 的 `const` 一样」 | **不一样**。C 里文件作用域 `const int c` 是**外部链接**，两个 TU 都写会 `multiple definition`；C++ 里是**内部链接**，不会 |

### A2 · 抽象机公理

> ### **C++ 的语义定义在一台「抽象机器」上，不是你的 CPU 上。**
>
> ### **UB（未定义行为）的意思是：程序在这台抽象机上没有任何行为定义。**

#### 与 A3 的关系：抽象机运行在对象模型的世界之上（不是并列，是定义域）

A2 与 A3 **不是平行的两条公理**——A2 定义在 A3 之上：**抽象机的状态 = 这个世界的对象及其值**（标准文本直说此）。所以「UB」的更准翻译是：

> **「A3 世界的某个状态，在 A2 里没有行为定义」**（不是"结果随机"）。

标准里的每一条规则几乎都是 A3×A2 的**合写**，拆开就成不了句：

| 标准里的一句话 | A3 负责的部分 | A2 负责的部分 |
| --- | --- | --- |
| 生命周期结束后访问对象 → UB | 生命周期 | 该状态无行为定义 |
| `reinterpret_cast` 后按新类型访问违反 strict aliasing → UB | 类型 | 裁决 |
| `placement new` 允许在同一存储上终结并重启对象的生命周期 | 存储与生命周期解耦 | 判定"合法" |
| as-if：优化器可改对象值，只要可观测行为不变 | 对象的存储与值 | 可观测行为 = 抽象机行为 |

**推论**：为什么「对象四元组」（A3）要把**存储**和**生命周期**分开？因为（A2 的）规则是以**对象**为单位、不是以内存块为单位说话的——同一块存储可以承载先后两段不重叠的生命周期（`placement new`）。这是 A2 倒逼 A3 结构的最有力证据。

#### 为什么这是公理

这是 C++「零开销抽象」承诺的另一面。为了让优化器能做激进的重排、删除、向量化，标准必须给它留出空间——这个空间就是 UB：

> 只要你的程序不触发 UB，优化器保证结果和抽象机上一致（**as-if 规则**）。
> 一旦触发 UB，**优化器被允许假定它不会发生**，并据此把代码改得面目全非。

#### 关键理解：UB 的后果是「整个程序」，不是「那一行」

这是最反直觉、也最重要的一点。经典的例子：

```cpp
int f(int x) { return x + 1 > x; }   // 有符号溢出是 UB
```

`-O2` 下 gcc 会把它编译成 `return true;`（`movl $1, %eax; ret`）。
推理链是：**「如果发生了溢出，那是 UB，此时程序怎么跑都合法；所以我只需保证不溢出时正确；不溢出时 `x+1 > x` 恒真。」**

所以：**UB 让优化器可以把「你的整个程序」当成一台它认为合理的机器来编译。**
「这段代码在 `-O0` 下是对的」不能作为任何证据。

#### 必修清单（在 CAE/EDA 代码里高频出现）

| UB | 典型形态 |
| --- | --- |
| 有符号整数溢出 | `int` 循环计数溢出；`-fwrapv` 可以禁用它（但那是扩展） |
| 数组/vector 越界 | `v[i]`（`operator[]` **不做检查**）；`v[v.size()]` |
| 悬垂指针 / 悬垂引用 | 返回局部变量的引用；`shared_ptr` 循环引用不算（那是泄漏） |
| 读未初始化值 | `int x; if (x > 0)`；`malloc` 出来的内存 |
| **strict aliasing 违反** | 用 `int*` 去读 `float` 的内存；用 `reinterpret_cast` 做类型双关 |
| **data race** | 两个线程无同步地访问同一内存、至少一个写。**C++11 起这是 UB，不是「结果不确定」** |
| 未定义顺序的求值 | `i = i++ + ++i;`；函数参数的求值顺序未指定 |

#### 实用工具

```bash
# 把 UB 从"静默"变成"报错"（开发期必开）
g++ -std=c++17 -g -O1 -fsanitize=address,undefined -fno-omit-frame-pointer prog.cpp -o prog

# 数据竞争检测
g++ -std=c++17 -g -O1 -fsanitize=thread -pthread prog.cpp -o prog
```

`basic_content/volatile`（部分）· `basic_content/pointer_refer`（悬垂引用）· `basic_content/union`（类型双关）· `concurrency/*`（data race）· `learn_class/modern_cpp_30/memorymodel_atomic`

#### 常见误解

| 误解 | 真相 |
| --- | --- |
| 「UB 就是「结果不确定，可能是垃圾值」」 | 不是「不确定」，是**「没有定义」**。优化器可以删掉整个代码路径、假定分支不可达 |
| 「`reinterpret_cast` 只是重新解释比特」 | 它是**编译器层面的类型声明**。用 `int*` 读 `float` 对象违反 strict aliasing ⟹ UB。C++20 起用 `std::bit_cast`，之前用 `memcpy` |
| 「`volatile` 能保证线程安全」 | **不能**。`volatile` 只阻止编译器把**这一次访问**优化掉/合并，它**不提供原子性、不提供内存序**。并发同步必须用 `atomic`/`mutex` |

### A3 · 对象模型公理

> ### **一个对象同时有四个彼此独立的属性：**
>
> ### **存储（storage）· 生命周期（lifetime）· 类型（type）· 值（value）**

#### 与 A2 的关系：这是抽象机的「世界」

A3 描述**世界里有什么**；A2 描述**这个世界怎么运行**。前者是本体论，后者是语义引擎——**A2 的状态空间就是 A3 的对象**。这就是为什么「生命周期结束后的访问 → UB」这类句子必须两者同时在场才成立：生命周期是 A3 的词，"没有行为定义"是 A2 的词。

#### 为什么这是公理

C++ 的对象模型选择了「**让这四个属性可以独立操纵**」——这是它与 Java/Python 等「一切皆引用 + GC」模型最根本的分歧点，也是理解 C++ 一切「坑」的总钥匙。

#### 四元组的分工（实测数据）

```text
class Empty {};
class EBO : Empty { int x; };            // 空基类
class NoEBO { Empty e; int x; };         // 空成员

sizeof(Empty) = 1     ← 对象必须有唯一地址 ⇒ 最小 1 字节
sizeof(EBO)   = 4     ← 空基类被优化掉（EBO）
sizeof(NoEBO) = 8     ← 成员子对象不能优化 ⇒ 空成员仍占 1 字节 + 3 字节对齐填充
```

**同一件事（空类），放在「基类」位置和「成员」位置，结果不同。**
这就是「存储」属性被独立操纵的直接体现——也是 `std::vector` 的 allocator 存储、`compressed_pair`、各种库设计技巧的根本原因。

#### 一切「那些事」都是四元组的切面

| 仓库章节 | 本质上在操纵 |
| --- | --- |
| `sizeof` · `union` · `bit` | **存储与布局** |
| `vptr_vtable` · `virtual` · `struct_class` · `abstract` | **类型与布局** |
| `const` · `volatile` · `explicit` · `enum` | **类型**（不是值！） |
| `static` · `this` | **生命周期 与 链接性** |
| RAII · 智能指针 · `copy-swap` · `pImpl` | **生命周期 与 值** |
| `reinterpret_cast` · placement new · union 类型双关 | **强行解耦**（所以危险） |

> **审代码时的用法**：看到一个 bug，先问「这四个属性里，哪一个是错的？」
>
> - 崩在析构 / 泄漏 / 重复释放 → **生命周期**问题
> - 数据在拷贝后被改动 / 改了共享状态 → **值 vs 引用语义（所有权）**问题
> - 读到的字节不对 / `sizeof` 不对 → **存储与布局**问题
> - 调用到了错误的函数 / 不懂为什么走了这个分支 → **类型（分派）**问题

#### 派生出的几条硬规则（都是 A3 的必然结果）

1. **对象必须唯一可寻址** ⟹ 非位域对象 `sizeof >= 1`；不同对象地址不同。
2. **生命周期从构造完成开始，到析构开始结束** ⟹ 在两者之外使用对象（含析构中调用虚函数）是 UB。
3. **类型决定怎么解释字节** ⟹ 同一块字节用不同类型访问，只有标准允许的少数情况才有定义（见 A2 的 strict aliasing）。
4. **基类子对象可以是 0 字节，成员子对象最小 1 字节** ⟹ EBO。

#### 仓库章节映射

`basic_content/sizeof` · `basic_content/vptr_vtable` · `basic_content/union` · `basic_content/bit` · `basic_content/struct_class` · `codingStyleIdioms/3_RAII`

#### 常见误解

| 误解 | 真相 |
| --- | --- |
| 「多继承只有一个 vptr」 | 多态对象里 vptr 的个数 = 它包含的**多态基类子对象**个数。实测 `class MA : public VA, public VB` → `sizeof(MA) == 16`，**两个 vptr、两张虚表** |
| 「编译器会重排成员来省空间」 | 标准只保证**同一访问控制段内**按声明顺序；Itanium ABI 承诺全部按声明顺序。实测 g++/clang **都不重排** |
| 「`vptr` 是从基类继承来的」 | 不是继承来的。每个多态对象在**构造时**被写入指向自己的虚表的指针 |
| 「`union` 只是省空间」 | C++ 的 union 有 **active member（活跃成员）** 概念：切换成员需要 placement new + 手动析构；读非活跃成员是 UB |

### A4 · 编译期 / 运行期分层公理

> ### **名字查找、类型检查、重载决议、模板实例化、内存布局 —— 全部是编译期的。**
>
> ### **运行期只剩三样：值、一次 vptr 间接跳转、栈/堆上的字节。**

#### 为什么这是公理

这是 C++「零开销抽象」的正面（A2 是它的背面）。**抽象的成本被全部转移到了编译期**。

#### 直接推论

1. **`virtual` 是唯一需要运行期信息的机制** ⟹ 它的运行期成本被压到极致：**一个指针 + 一次间接跳转**。实测：

```asm
call_ref(Base& b)     →  movq (%rdi), %rax        ; 取出 vptr
                         jmp  *(%rax)             ; 间接跳转到虚表[0]
```

**就这么多。** 没有哈希查找、没有字符串比较。（代价是不内联机会 —— 但见 T5 的去虚化。）

1. **`const` 不是编译期常量** —— 因为 `const` 说的是**类型**（T1），不是**值**。编译期常量是 `constexpr` 的活。
2. **「默认参数静态绑定、虚函数动态绑定」是必然的** —— 默认参数在调用点被填入，那是编译期的事；虚函数的目标要到运行期才知道。
3. **为什么模板「编译慢但跑得快」** —— 实例化在编译期完成，运行期没有任何额外成本。

#### 仓库章节映射

`basic_content/virtual`（默认参数一节）· `cpp2.0/cpp11/constexpr.cpp` · `learn_class/modern_cpp_30/compilercompute` · `learn_class/modern_cpp_30/compilerpoly`

#### 常见误解

| 误解 | 真相 |
| --- | --- |
| 「`const` 就是编译期常量」 | `const` 是类型限定（运行期只读），`constexpr` 才是编译期常量。`const int n = rand();` 完全合法 |
| 「虚函数一定要付出运行期代价」 | 只要编译器能**证明**动态类型（实际对象 / `final` / LTO / 推测去虚化），就能完全消除。实测见 T5 |
| 「`inline` 才能内联」 | 实测：未写 `inline` 的普通函数在 `-O2` 下照样被内联 |

### A5 · 资源公理（RAII）

> ### **资源 = 任何需要成对 acquire / release 的东西。**
>
> ### **C++ 的答案：把资源所有权绑到对象的生命周期上，用析构函数自动释放。**

#### 为什么这是「公理」而不是「技巧」

因为它是 **A3 的直接推论 + 一条语言保证**：

- A3 给了我们「生命周期是对象的独立属性」；
- 语言保证：**栈展开（stack unwinding）时，所有已构造的局部对象的析构函数一定会被调用**（即使正在抛异常）。

两条合起来 ⟹ **「用对象的生命周期管理资源」是类型系统强制执行的，不依赖程序员记得写 `finally`。**

#### 关键推论：异常的传播路径 = 析构的调用路径

这解释了两个仓库里没讲清的问题：

1. **为什么 C++ 不需要 `finally`** —— 析构函数就是 `finally`，而且是被编译器强制的。
2. **为什么 `copy-swap` 惯用法成立** —— 详见 T4。

#### 「资源」的范围（比你想的广）

堆内存、文件描述符、锁、socket、GPU 显存、MPI 通信子、**数据库事务**、**性能计时器、日志作用域、状态标志的临时修改**。

**判断标准**：只要你有「开始」和「结束」两个必须配对的动作，它就适合用 RAII 包一层。

#### 仓库章节映射

`codingStyleIdioms/3_RAII` · `codingStyleIdioms/4_copy-swap` · `codingStyleIdioms/5_pImpl` · `learn_class/modern_cpp_30/RAII` · `learn_class/modern_cpp_30/smart_ptr`

#### 常见误解

| 误解 | 真相 |
| --- | --- |
| 「析构函数不会抛异常，所以异常安全很简单」 | 析构函数**抛异常**会直接 `std::terminate`（因为它可能在栈展开中被调用）⟹ 析构函数必须 `noexcept`，且必须自己吞掉错误 |
| 「`shared_ptr` 用了就安全」 | `shared_ptr` 表达的是**共享所有权**。用来表达独占所有权会造成循环引用泄漏、以及无意义的原子引用计数开销。见 T4 的所有权三态 |
| 「RAII 就是「用智能指针」」 | 智能指针只是 RAII 的一个实例。**你自己写的 `class` 只要有析构函数，就是 RAII** |

### T1 · cv 限定是**类型**的属性，不是**值**的属性

**推出自**：A3（类型是独立属性）+ A4（类型是编译期的）

**陈述**：`const` 修饰的是**类型的读权限**，不是「这个值不会变」。因此：

- `const` 成员函数 = **`const T* const this`** ⟹ **这就是 `mutable` 存在的唯一理由**（需要一个「在 const 函数里也能改」的逃生舱）。
- 顶层 const 在函数**参数**上会被忽略 ⟹ `void f(const int)` 和 `void f(int)` 是**同一个函数**（不构成重载）。
- 非 const 对象可以调用 const 成员函数；const 对象**只能**调用 const 成员函数 ⟹ 这是 const-correctness 的传播机制。

**仓库章节**：`basic_content/const` · `basic_content/this` · `basic_content/volatile`

**注意 `volatile` 是另一回事**：它不是「更弱的 const」，而是「**每次都真的访问内存，不要优化掉**」。用于内存映射 I/O、`sig_atomic_t` 信号处理。**它和线程安全无关**（见 A2）。

### T2 · 生命周期决定析构时机，析构时机决定安全

**推出自**：A3 + A5

**陈述与实测**：

| 对象的存储期 | 构造时机 | 析构时机 |
| --- | --- | --- |
| 局部对象 | 执行到声明处 | 出作用域（**逆序**） |
| 函数内 `static` | **第一次执行到声明处**（惰性！），C++11 起**线程安全** | `main` 之后 |
| 全局 / 命名空间 `static` | 程序启动时（顺序**跨 TU 不确定**） | `main` 之后，**逆序** |

实测证据：

```text
$ ./magics
main start
S ctor          ← 只打印一次，尽管有两个线程同时调用 get()
```

```text
$ ./dtor
ctor g1
ctor g2
main
dtor g2         ← 逆序
dtor g1
```

**由此推出三个真实世界的灾难**：

1. **静态初始化顺序灾难（static initialization order fiasco）**：TU-A 的全局对象构造函数里用了 TU-B 的全局对象，而 B 还没构造 ⟹ UB。**修法：用「函数内 static」的惰性初始化替掉全局对象**（即 Meyers singleton 的原理）。
2. **静态析构顺序灾难**：同理，只是发生在关闭期。
3. **`static const int` 类内初始化的 ODR 陷阱**：类内给的是**值**不是**定义**，一旦被 odr-use（取地址 / 绑到引用）就变成 `undefined reference`。实测：

```text
$ g++ -std=c++11 st3.cpp
undefined reference to `A::k'          ❌
```

```cpp
struct A { static const int k = 7; };
int main(){ const int* p = &A::k; }    // 只是取了个地址
```

**修法**：C++17 起类内写 `static constexpr int k = 7;`（隐式 `inline`），或类外补一行定义。

**仓库章节**：`basic_content/static` · `codingStyleIdioms/3_RAII`

### T3 · 引用是**别名**，不是对象

**推出自**：A3（引用没有独立的存储/身份）

**陈述与必然推论**：

| 性质 | 为什么必然 |
| --- | --- |
| 必须初始化 | 别名必须指向某个已存在的东西 |
| 不能重绑定 | 赋值给引用是**改被引用对象**，不是改绑定 |
| `sizeof(ref) == sizeof(被引用类型)` | 因为引用不是对象，没有自己的大小 |
| 不存在「引用的引用」/「引用的数组」 | 同上；**引用折叠是模板推导期的规则，不是运行期实体** |
| 编译器不保证用指针实现 | 标准没有要求。内联后引用可能不物化任何存储 |

**引用折叠规则**（这是理解完美转发的唯一门槛）：

```text
X& &   →  X&
X& &&  →  X&
X&& &  →  X&
X&& && →  X&&
```

**记忆法**：只要有**一个**左值引用参与，结果就是左值引用。

**最实用、仓库完全漏掉的一条 —— 临时对象生命周期延长（lifetime extension）**：

```cpp
const std::string& r = std::string("hi");     // ✅ 延长到 r 的生命周期
std::string&&      r2 = std::string("hi");    // ✅ 同样延长

// 但以下都不延长：
const std::string& bad1 = f().substr(0, 2);   // 延长的是 substr 的返回临时量，不是 f() 的内部
auto bad2 = []{ const std::string& r = std::string("x"); return r; }();  // 返回时已悬垂
struct S { const std::string& m; S(): m(std::string("x")) {} };          // 成员引用不延长
```

**规则**：延长只发生在**「引用直接绑定到临时对象」**这一种句型上（且限于局部 `const T&` / `T&&`）。一旦经过函数返回、成员初始化、返回值推导，延长不成立。

**仓库章节**：`basic_content/pointer_refer` · `learn_class/modern_cpp_30/reference`

### T4 · 拷贝 = 复制语义，移动 = 窃取语义

**推出自**：A3（值与生命周期是独立属性）+ A5（所有权）

**陈述**：

- **拷贝**：新对象获得**等价的**值，源对象**不变**。
- **移动**：新对象**接管**源的资源，源进入「**有效但未指定（valid but unspecified）**」状态——**不得**假定它为空，只能对它赋值或析构。
- **所有权三态**（这是审 AI 代码的关键尺子）：

| 所有权语义 | C++ 类型 | 何时用 |
| --- | --- | --- |
| **独占** | `unique_ptr` / 值成员 | **默认选它**。CAE/EDA 里 90% 的场景 |
| **共享** | `shared_ptr` | 只有确实需要「多个所有者，寿命不确定」时 |
| **借用（不拥有）** | `T*` / `T&` / `span` / `string_view` | 函数参数。**必须**由文档/命名保证生命周期 |

- **rule of 0 / 3 / 5**：
  - **rule of 0**：不写任何特殊成员函数，全部用 `= default` 或依赖编译器 ⟹ **最优**。
  - **rule of 3**（C++98）：析构、拷贝构造、拷贝赋值三个要么都写，要么都不写。
  - **rule of 5**（C++11）：加上移动构造、移动赋值。
  - **陷阱**：声明了析构函数 ⟹ 移动操作**隐式被删除**（不是不生成，是 `delete`），拷贝操作仍隐式生成（已弃用）。**所以「只加一个虚析构」会让类悄悄失去移动能力。**

- **`copy-swap` 为什么成立**：先拷贝到临时量（失败时原对象不变），再 `swap`（`noexcept`）⟹ 天然满足**强异常安全保证**。这是 A5 的直接应用。

**仓库章节**：`cpp2.0/cpp11/move.cpp` · `cpp2.0/cpp11/rvalue.cpp` · `codingStyleIdioms/4_copy-swap`

### T5 · 分派有三层

**推出自**：A4（编译期 vs 运行期分层）

| 层 | 机制 | 决议时机 | 运行期成本 |
| --- | --- | --- | --- |
| 1 | **重载**（overload） | 编译期 | 0 |
| 2 | **模板**（template / CRTP / `if constexpr`） | 编译期 | 0 |
| 3 | **虚函数**（virtual） | 运行期 | **1 次间接跳转** |

**去虚化（devirtualization）—— 实测证据**：

```cpp
struct Base { virtual int f() const { return 1; } virtual ~Base() = default; };
struct Derived : Base { int f() const override { return 2; } };
struct Sealed final : Base { int f() const override { return 3; } };

int call_ref(Base& b)      { return b.f(); }        // 动态类型未知
int call_local()           { Derived d; Base& b = d; return b.f(); }  // 动态类型已知
int call_final(Sealed& s)  { return s.f(); }        // final ⇒ 没有更远的覆写
int call_direct(Derived& d){ return d.f(); }
```

`-O2` 实测汇编：

```asm
call_ref(Base&):                  ; 真动态派发
    movq (%rdi), %rax
    jmp  *(%rax)

call_local():                     ; 完全消除
    movl $2, %eax
    ret

call_final(Sealed&):              ; 参数是"引用"，但完全消除！
    movl $3, %eax
    ret

call_direct(Derived&):            ; 推测去虚化：先猜，猜错再跳
    movq (%rdi), %rax
    leaq _ZNK7Derived1fEv(%rip), %rdx
    movq (%rax), %rax
    cmpq %rdx, %rax
    jne  .L8
    movl $2, %eax
    ret
.L8:
    jmp  *%rax
```

> **结论**：仓库说「虚函数只有在有实际对象而非引用时才能内联」是**错的**。`call_final` 的参数就是引用，照样完全消除。**真正的判据是「编译器能否证明动态类型」**，`final` 就是给编译器的一个证明。

**虚函数的三条硬约束（都来自 A3/A4）**：

1. **构造函数不能是 virtual**（不是「vptr 还没建好」这个后果，而是本质原因：**虚派发要求「存在一个已有动态类型的对象」，而构造函数的任务正是「把裸存储变成一个对象」**）。
   ⟹ **实用推论**：**在构造函数里调用虚函数不会派发到派生类的覆写**（此时动态类型还是当前正在构造的类）。这是仓库完全没提、但实际代码里高频踩的坑。
2. **静态成员函数不能是 virtual**：没有 `this`，没有对象，无从派发。
3. **析构函数可以是、且在「打算通过基类指针 delete」时应该是 virtual**。但反过来：**不要无脑给所有基类加虚析构**——加了会让类多一个 vptr，并**隐式删除移动操作**。设计成「不该被多态删除」的基类，标准做法是 **protected 非虚析构**。

**仓库章节**：`basic_content/virtual` · `basic_content/vptr_vtable` · `basic_content/abstract` · `basic_content/c_poly`

### T6 · 成员函数的「定义位置」决定它的链接性

**推出自**：A1

**陈述**：**在类体内部定义的成员函数，隐式是 `inline`；在类体外定义的，按普通函数规则。**

这是 A1 的直接落地，也是「哪些东西能放头文件」的完整答案：

| 写在头文件里的东西 | 可以吗 | 依据 |
| --- | --- | --- |
| 类内定义的成员函数 | ✅ | 隐式 `inline` |
| 类外定义、带 `inline` 的函数 | ✅ | 显式 `inline` |
| 模板函数 / 类模板的成员函数 | ✅ | 模板实例**隐式** `inline`（实测 `W` 弱符号） |
| `constexpr` 函数 | ✅ | 隐式 `inline`（实测 `W` 弱符号） |
| C++17 `inline` 变量 / `static inline` 成员 | ✅ | C++17 起 `inline` 可用于变量 |
| **普通函数定义** | ❌ | 强符号 `T` ⟹ `multiple definition` |
| **普通全局变量定义** | ❌ | 同上 |
| **`static` 成员变量的类外定义** | ❌ | 只能出现在**恰好一个** `.cpp` |

实测（同一头文件被两个 TU 包含）：

```text
版本1：int add(int,int){...}          → multiple definition of `add(int, int)'   ❌
版本2：inline int add(int,int){...}   → 链接成功                                  ✅
```

**仓库章节**：`basic_content/inline`

### T7 · 值类别 + 引用折叠 ⟹ 完美转发

**推出自**：A4（编译期决定）+ T3（引用折叠）

**为什么需要这一条**：这是 C++11 之后代码里最常见的「看着懂、说不出为什么」的一段。它是**纯编译期的代数**，没有运行期成本。

**三件事必须分清**：

| 概念 | 说的是什么 | 判据 |
| --- | --- | --- |
| **类型** | `int` / `int&` / `int&&` | 声明的形态 |
| **值类别** | 左值 / 纯右值 / 将亡值 | **表达式**的属性，不是变量的属性 |
| **转发引用** | `T&&` 且 `T` 是**被推导的模板参数** | 只看这个句型 |

**转发引用是「类型推导 + 引用折叠」的组合技**：

```cpp
template <class T> void f(T&& x);   // 转发引用（T 被推导）
void g(int&& x);                    // 右值引用（类型固定，不是转发引用）
```

- 传左值 `int a; f(a);` → `T` 推导为 `int&` → `T&&` = `int& &&` → 折叠成 `int&`
- 传右值 `f(1);` → `T` 推导为 `int` → `T&&` = `int&&`

**然后 `std::forward<T>(x)` 的唯一作用是**：在展开时把 `x` 还原成它原本的值类别。**它不是「转换」，是「还原」。**

**这就是为什么 `std::move` 的名字是骗人的**：`std::move` **不移动任何东西**，它只是一个把左值转成右值的 `static_cast`。

**仓库章节**：`cpp2.0/cpp11/rvalue.cpp` · `cpp2.0/cpp11/move.cpp` · `learn_class/modern_cpp_30/reference`（`forward.cpp` · `collapses.cpp` · `lifetime.cpp`）· `cpp2.0/cpp11/decltype.cpp`

### T8 · 类型是**编译期的代数**（限定 / 推导 / 转换 三种运算）

**推出自**：A4（类型是编译期概念）+ T1（cv 是类型属性）+ T7（值类别）

**陈述**：类型系统不是一堆标签，而是一套**只有三种运算的代数**：

```text
① 限定（qualify）：加/去 cv、加/去引用（左/右）
② 推导（deduce）：从表达式反推类型 —— auto / decltype / 模板推导 **同源**
③ 转换（convert）：类型之间能否过去、代价多少（转换序列）
```

**推论（把散落的知识点串成一串）**：

| 现象 | 用哪个运算解释 |
| --- | --- |
| 顶层 const 不进签名，底层 const 进 | ① 限定 + ② 推导：实参推导会剥掉顶层 cv（所以调用方看不出差别） |
| 重载决议为何要“排序” | ③ 转换：排序就是在比转换序列的代价 |
| `auto x = expr;` 与 `decltype(expr)` 不同 | ② 推导：`auto` **按值**（去引用去 cv）；`decltype` **保形**（保留引用与 cv，含 `decltype((x))` = 引用） |
| 模板推导与 auto 惊人地像 | ② 推导：**同一套规则**（除 `initializer_list` 与 `{}` 等少数差异） |
| `{}` 能拦窄化，`()` 不能 | ③ 转换 + 初始化：花括号禁止“有损”转换（非 const 降为 warning，常量是硬错误） |

**失效前提**：代数只在编译期；运行期没有“类型代数”——运行期选函数靠的是 T5（vptr）。**两条平行机制，别混。**

**仓库章节**：`decltype` · `cpp2.0/cpp11/auto.cpp` · `enum`（隐式转换）· **`22-语言核心暗角.md`**（名字查找与重载四步）

### T9 · 接口即契约（五类契约，缺一类就是一个隐患）

**推出自**：A1（链接契约）+ A5（所有权）+ T1（const 契约）+ T4（移动语义承诺）

**陈述**：一个 C++ 接口 = 五类**承诺/要求**的集合；读、写、审接口，就是逐条检查这五类是否明确。

| # | 契约 | 内容 | 由谁检查 | 缺失的后果 |
| --- | --- | --- | --- | --- |
| 1 | **类型契约** | 签名、`const`、`explicit`、返回类型 | 编译期 | 隐式转换/误用 |
| 2 | **所有权/生命周期** | 谁拥有、借用能活多久（三态） | 编译期 + 约定 | 悬垂/泄漏/双重释放 |
| 3 | **异常契约** | `noexcept` 还是不抛；错误用何机制 | 运行期（违约=terminate） | 性能退化/terminate |
| 4 | **ABI 契约** | 二进制稳定性（导出的类/模板/内联） | 链接期 | 跨 .so 崩（19） |
| 5 | **时序契约** | 线程安全、可重入、调用顺序、阻塞与否 | 运行期 | 数据竞争/死锁/饿死（11/17） |

**推论（三条实用判据）**：

```text
· 契约缺失 = 隐含耦合或隐含 UB：例如“未标注线程安全”的类被多线程用，不是“文档没写”，是**契约缺失**。
· 五类契约分属不同检查期：类型/编译期，异常/运行期，ABI/链接期，时序/运行期 —— 所以“一次静态检查”永远不够（对比 24 的五层关卡）。
· **时序契约是文档最常缺的一类**：ROS2 回调的“可重入要求”（17）就是时序契约；`const` 成员函数“线程安全承诺”也是（C++11 起标准库约定）。
```

**失效前提**：契约只在“双方都遵守”时成立；C++ 不强制运行时检查（除了 `noexcept` 违约=terminate 这种硬线）。

**仓库章节**：`const` · `explicit` · `virtual`（虚析构=生命周期契约）· **`09`/`16`/`17`/`19`/`24`**（五类契约各自的展开）

### T10 · 求值有确定的**顺序模型**（这就是并发 happens-before 的单线程原型）

**推出自**：A2（抽象机的时间维度）

**陈述**：表达式求值不是“一堆无顺序的动作”，而是有**偏序**：

```text
sequenced-before（先于）：如同一语句内的确定顺序（① 全表达式结束时副作用完成）
indeterminately sequenced（不确定序但不相交）：函数实参之间——**要么先A后B，要么先B后A，但不会交错**
unsequenced（未排序）：同一标量对象上多个修改 → **UB**
```

**推论**：

| 现象 | 结论 | 实测/依据 |
| --- | --- | --- |
| `i = i++ + 1` | **C++17 起有定义**（右操作数先于左）：C++11/14 是 UB | 实测两版本输出都是 1，且 GCC 的 UBSan **不诊断**（→ 不诊断 ≠ 有定义） |
| `printf("%d %d", i++, i++)` | **未指定顺序**（C++17 起；之前是 UB） | 实测输出 `1 0`（**右到左**） |
| `f() + g()` | 同上：实测 `f g`（**左到右**） | 同机不同上下文结果相反 → **证明“未指定”** |
| 两条语句之间 | 全序（上一条的副作用已完成） | 标准 |

**实用结论（写代码的硬规则）**：

```text
· 同一表达式里不要对同一对象既读又写（哪怕当前标准允许，可读性也很差）
· 函数实参的求值顺序**不可依赖**（同机同编译器都可能因上下文不同而变）
· 把“顺序”写成两语句，而不是靠逗号/括号碰运气
· 这条偏序就是并发那套 happens-before 的**单线程版本**（11）——同一套思维，两个尺度
```

**仓库章节**：`volatile` · `assert`（副作用）· **`11-并发与内存模型体系.md`**（把它推到多线程）

### T11 · 抽象机必须落到真实机器上（**实现模型**）

**推出自**：A2（抽象机）+ A3（对象布局）

**陈述**：标准只定义抽象机行为；**落地由 ABI 完成**——调用约定、栈帧、对象布局、vtable、名字修饰。
标准“未规定”的部分，由**事实标准**（Itanium C++ ABI）稳定下来。

**推论**：

```text
· 为什么 sizeof/偏移/vtable 是“实现定义但可预测”：标准放权，ABI 接住（实测：多继承两个 vptr、EBO=0 字节）
· 为什么跨编译器/平台要重测：“未规定”不等于“不稳定”，但**保证只在同一 ABI 内**
· 为什么 ABI 兼容是工程约束（19）：换编译器/加 -DNDEBUG/改内联，都可能破 ABI
· 为什么 -march=native 不可移植：它直接改变“抽象机→机器”的映射选择
```

**失效前提**：ABI 是**约定**不是标准；不同 ABI（MSVC vs Itanium）的二进制**不可混用**。

**仓库章节**：`sizeof` · `vptr_vtable` · **`05`（看布局/汇编的命令）** · **`19`（插件/ABI 语言）** · **`22 §4`（ODR/ABI 判据）**

### T12 · 程序有**生命周期**（启动 → main → 终止）

**推出自**：A3（对象生命周期）+ T2（析构时机）+ A5（资源）

**陈述**：程序自己在时间轴上也有阶段顺序，而且**跨翻译单元的顺序是未指定的**：

```text
静态初始化：TU 内按声明顺序；**跨 TU 顺序未指定**（跟链接顺序有关）
    ↓
main()
    ↓
静态析构：**逆序**（后构造先析构）
    ↓
atexit 注册的函数
```

**推论（三个真实灾难，都能实测）**：

| 灾难 | 机制 | 解药 |
| --- | --- | --- |
| **静态初始化顺序灾难** | TU-A 的全局对象构造器里用了 TU-B 的全局对象，而 B 还没构造 → 读到未初始化 | 换成**函数内 static**（惰性 + C++11 起线程安全）——Meyers 单例的原理 |
| **静态析构顺序灾难** | 同因，发生在关闭期（析构时访问已销毁对象） | 同上；或根本不用全局对象 |
| **静态初始化依赖未定义行为** | 跨 TU 顺序**未指定**，不是“按源码顺序” | 消除跨 TU 初始化依赖 |

**实测（一看就懂）**：

```text
$ g++ g1.cpp g2.cpp -o f1 && ./f1     # 链接顺序 g1 g2
A ctor
B ctor, reads A=42                    ← 正常

$ g++ g2.cpp g1.cpp -o f2 && ./f2     # 链接顺序反转
B ctor, reads A=0                     ← 灾难：读到未初始化的 a
A ctor
```

**失效前提**：“函数内 static 线程安全”是 **C++11 起**；之前需手动双检查锁。

**仓库章节**：`static`（含 issue #142）· **`codingStyleIdioms/3_RAII`** · 与 T2 配套读

## 第 3 层 · 三条元原则

> 前面是「世界是怎样运行的」（描述性），这三条是「**遇到新问题该怎么判断**」（规范性）。审 AI 生成的代码时，它们是最上层的过滤器。

### 元原则 1 · 零开销抽象

> **你不用的东西，不该让你付出代价；你用了的东西，不该比手写更慢。**

**这是 A2（UB）和 A4（编译期分层）背后的**动机**。

**它的解释力**：

- 为什么允许 UB？因为要给优化器留空间 —— 零开销。
- 为什么 `virtual` 只是一个指针 + 一次跳转？因为多态必须付的代价不能超过手写函数指针表。
- 为什么模板没有运行期开销？因为实例化全在编译期。
- 为什么有 EBO？因为「不用的空基类不该占字节」。

**它的反向用法（审代码）**：**看到「为了性能」而写的复杂代码时，问一句「这个抽象真的被消除了吗」**，然后用 `05` 的工具箱去看汇编。

---

### 元原则 2 · 显式优于隐式；让类型系统承载约束

> **能用类型表达的约束，不要用注释表达，更不要用「约定」表达。**

**这是 C++11 之后所有新特性的共同主题**：

| 特性 | 它替代了什么隐式危险 |
| --- | --- |
| `explicit` | 单参构造函数的隐式转换 |
| `enum class` | 无作用域枚举隐式转 `int` |
| `override` | 拼错函数名导致「悄悄没覆写」 |
| `final` | 意外的进一步继承 / 让编译器能去虚化（见 T5） |
| `nullptr` | `0` / `NULL` 在重载决议中的歧义 |
| `const` 成员函数 | 用注释写「这个函数不改对象」 |
| `noexcept` | 用注释写「这个函数不抛异常」（且它影响容器选择移动还是拷贝） |
| `= delete` | 用注释写「不要用这个重载」 |
| `static_assert` | 运行期的 `assert` |

**审 AI 代码的第一招**：**看它有没有把约束写进类型里**。
AI 生成的代码最常见的系统性缺陷就是——**语法正确、逻辑能跑，但把所有约束都退化成运行期的注释和 `if` 判断**。

---

### 元原则 3 · 能编译期算的，不要留到运行期

**这是 A4 的主动用法**：

| 手段 | 把什么搬到了编译期 |
| --- | --- |
| `constexpr` / `consteval` | 数值计算、查表 |
| `constexpr if` / 模板特化 | 分支选择 |
| `static_assert` | 类型约束检查 |
| 模板元编程 / CRTP | 多态派发（静态多态，见 T5） |
| `if constexpr` + `requires`（C++20） | 重载决议 |

**对审代码的直接价值**：AI 生成的代码常常**在运行期做本可以在编译期做完的事**——比如运行期的 `switch` 去判断一个编译期就已知的类型，或者运行期算常量表。这是「能跑但浪费」的典型形态。

---

## 附 · 框架的边界（本框架**不**覆盖什么）

> **本表是 0.5.4「四域分类」在 C++ 上的具体落地**——给那些「该被承认而不是被解释」的内容指明去处。

诚实地标出边界，比假装什么都能解释更有用。

| 不覆盖 | 该去哪学 |
| --- | --- |
| **标准库的容器/算法选择、复杂度** | 需要单独一张「数据结构 + 复杂度」表；仓库 `src_analysis/stl` 只讲实现，不讲选择 |
| **构建系统、工具链、ABI 细节** | 本框架只提供「怎么验证」的方法，不提供「构建系统怎么配」 |
| **数值方法、稀疏矩阵、并行算法** | 领域知识，与 C++ 语言规则正交 |
| **并发算法的设计**（不只是一致性规则） | `01` 的 A2 只给了「什么是 UB」，不给「怎么设计无锁结构」 |
| **C++20 模块（modules）** | 会改变 A1 的一部分（不再需要头文件 + `inline` 的老套路），本框架基于传统头文件模型 |
| **具体 ABI 的数字**（偏移、`sizeof`） | 本框架给的是**推导规则**；具体数字必须用 `05` 实测，因为它们是实现定义 |
