# 14 · 调试与排错体系

> **场景**：崩了 / 错了 / 慢了 / 挂死了，不知道从哪下手；`-O0` 对 `-O2` 错；AI 代码反复出同类问题。
> **挂靠**：A2（UB 是静默的）· A1（链接错误）｜**学**：04 第 3 课 · 05 工具箱 · 07 图谱⑬｜**记**：08 L3 命令查表 + 反例档案

---

## 0 · 这个体系解决什么问题

调试不是"盯着代码猜"，是一条**以工具为先的排查流水线**。这套体系按**现象分类**给你对应的第一反应，把「崩/错/慢/挂死」四种症状各对应到工具与根因域。

> **第一原则（A2 的直接推论）**：UB 是静默的——**越界读不保证崩溃**（本机实测：越界读打印正常值退出）。所以**不要等崩溃来暴露错误**，要主动用工具（sanitizer）扫。

---

## 1 · 分层排查流水线（先工具，后代码，最后才"读"）

```text
第 0 层  让编译器先说话（30 秒，永远先做）
         -Wall -Wextra -Wpedantic -Wshadow -Wconversion -fsyntax-only
         -flto -Wodr（跨 TU 的 ODR，08 实测能抓 类型不一致）
第 1 层  UBSan + ASan（开发/测试期必开）
         越界/悬垂/泄漏/溢出/别名 → 立即报；本机实测：静默 UB 变成"runtime error + ERROR: AddressSanitizer"
第 2 层  崩溃定位 → gdb（bt → 上一帧 → 变量）
第 3 层  并发问题 → TSan（本机用 setarch -R 修 ASLR，08 已录）
第 4 层  性能 → 计时/perf + 一次只改一处（13 §3）
第 5 层  这才是"读代码"：带着上面工具指出的具体位置回来读
```

**规矩**：永远先跑第 0~1 层——大部分"A 类 bug"（内存/UB/ODR）在它们那里直接被点名，不用人肉找。

## 2 · 现象 → 根因域决策树

```text
症状分类
├─ 崩溃
│   ├─ SIGSEGV        → 指针/引用/越界/悬垂 → gdb bt + ASan
│   └─ abort/terminate → 异常无人接/noexcept 内抛/析构抛/assert → 找 terminate 的 where（set_terminate/backtrace）
├─ 值不对但没崩
│   ├─ -O0 对 -O2 错 → 99% 是 UB（A2）→ UBSan/ASan 扫 → 找不到就 -O1 + ASan 逐层
│   ├─ 多线程"偶尔"  → data race → TSan（x86 `int++` 假象是经典，08）
│   └─ 数值有偏差    → 浮点精度/消去误差（13 §2 浮点）→ 用更好算法，非语言 bug
├─ 慢
│   ├─ 全局性慢      → 优化等级/算法（13 §1.1）
│   ├─ 热点函数慢    → 13 §3 五步（先测）
│   └─ 卡顿/偶发     → 分配/Cache miss/锁竞争 → perf/计时 + TSan 顺带看锁
└─ 挂死（卡住）
    ├─ 死锁          → 锁序 → gdb thread apply all bt（看互相等谁的锁）
    └─ 等待永不满足  → condition_variable 忘 notify / 条件永不成立 → 断点看 predicate
```

## 3 · gdb 最小可用集（够用的 10 个命令）

```text
gdb ./prog              启动（建议 -g 编译）
run [args]              运行
bt                     打印调用栈（崩溃后的第一动作！）
frame N / up / down    切换/移动帧
info locals / p expr   看局部变量/任意表达式
x/wf 0x...             看内存：x/16g addr（16 个 8 字节）
break file:line / b fn 断点
catch throw            在异常抛出点停下（找"谁抛的"神器）
watch var              数据被改时停下（找"谁改了它"）
thread apply all bt    挂死时所有线程的栈（找死锁）
```

**实测演示**（本会话）：分段错误的 gdb 批处理输出

```text
Program received signal SIGSEGV, Segmentation fault.
#0  ... in sum (m=...) at segv.cpp:3
#1  ... in main () at segv.cpp:4
s = 0
```

**注意**：bt 只告诉你**症状帧**（在哪崩），根因（`m.data` 未初始化）要 `p m` / 往调用者看——**bt 之下再往上一帧问"调用者给了什么"**。

## 4 · 常见坑（以为自己在调试，其实在浪费时间）

| 坑 | 为什么错 | 正解 |
| --- | --- | --- |
| 关了优化复现 bug | `-O0` 让 UB 消失/变形（A2） | **在 `-O1/-O2 + sanitizer` 下复现** |
| 死盯代码猜根因 | 你对 20 行的推理，sanitizer 1 秒给出位置 | 先工具后代码（§1） |
| "跑对了 = 没 bug" | x86 单指令 RMW 假象（08） | 证据靠 TSan/持久化测试 |
| 一次改多处再测 | 分不清哪处起作用 | 一次改一处（13 §3） |
| 崩溃后再编译 | 忘了 -g | 开发期永远 -g + sanitizer |
| 只看顶层错误 | g++ 报错链里根因常在中下部 | `-fsyntax-only` 从第一个错误起看 |
| 遇到链接错误只查名字 | 改完还是错 | nm/readelf 看符号；`-flto -Wodr`（08） |
| 用注释解释行为 | 掩盖问题 | 修行为或留 TODO + 反例档案（08） |

## 5 · 实践关联（动手清单）

```bash
# ① 复现"越界读不崩"（08 反例）——证明为什么要用工具
g++ -std=c++17 -g -O0 /tmp/v2/crash.cpp -o crash && ./crash   # 打印 2.000000 正常退出！
g++ -std=c++17 -g -O1 -fsanitize=address,undefined /tmp/v2/crash.cpp -o crash_san && ./crash_san
#   → runtime error: index 6 out of bounds ... ERROR: AddressSanitizer: stack-buffer-overflow（在越界的 UB 处停下）

# ② 复现分段错误 + gdb bt（本会话实测流程）
g++ -std=c++17 -g -O0 /tmp/v2/segv.cpp -o segv
gdb -batch -ex run -ex "bt 4" -ex "info locals" ./segv

# ③ catch throw：让 gdb 在"谁抛的"处停
g++ -std=c++17 -g -O0 /tmp/v2/exc.cpp -o excg
gdb -batch -ex "catch throw" -ex run -ex "bt 3" ./excg

# ④ 死锁演示：gdb thread apply all bt（两个线程互等锁）
```

## 7 · 自测三问

- **判定**：越界读在 `-O0` 下"没崩"，能据此说"没 bug"吗？（不能——UB 静默，`-O2`/sanitizer 下现形）
- **预测**：`-O0` 复现不了的崩溃，在 `-O1 + ASan` 下会怎样？（常常直接报出来——因为优化暴露了未定义的模式）
- **构造**：写一个包含三个 bug 的小程序（越界、未初始化读、死锁），用本体系的流水线分别抓出来，记录每层工具的输出。
